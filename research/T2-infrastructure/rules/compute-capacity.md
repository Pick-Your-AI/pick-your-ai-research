# Proposed GPU / compute compatibility rules

Issue: #10 · Contract review: #40 · Status: proposed / unverified · Proposal version: 0.3.0

Evidence IDs refer to [gpu-compute.md](../gpu-compute.md), all accessed 2026-10-16. This is a research proposal using the [shared template](../../../templates/rule-proposal.md), not an approved Ruleset. `pass`, `fail`, `unknown`, `skipped` are **outcomes**. `info`, `warning`, `error` are separately **severities**. No rule below is claimed verified joint compatibility: [governance](../../../docs/governance.md) requires a second source or reproducible test. Arithmetic assertions reproduce the proposed formula but do not test a model/runtime on hardware.

This revision applies the [#3/#40/#41 owner review of PR #75](https://github.com/Pick-Your-AI/pick-your-ai-research/pull/75#pullrequestreview-5550616927), reviewed head `9e66622a4b2698a9305274f05da9c15ae5d90b8c`, accessed 2026-10-17. Acceptance into the review queue is not approval of an executable ruleset. CD-1/CD-2/CD-3 remain proposed contract work; no new field below is silently added to v1.

Each clause has its own proposed ID and fixed severity. COMPUTE-01–04 separate `compute-NN.constraint` (`error`), `compute-NN.evidence` (`warning`) and `compute-NN.applicability` (`info`). The constraint keeps severity `error` on every outcome and uses proposed `on_unknown: review`. The evidence clause records eligibility separately from independent verification; checked, eligible publisher documentation can support `pass` while the result remains **unverified**. Missing eligible evidence gives `unknown`, with `on_unknown: review`. Applicability is `pass/info` for known applicable scope, `skipped/info` for known non-applicable scope and `unknown/info` for missing scope, with `on_unknown: defer`. #40 will collapse redundant evidence/applicability clauses into reason codes under CD-1; the current clause split is retained pending that versioned change.

## Shared applicability (formerly COMPUTE-05)

Apply COMPUTE-01–04 to the **serving component's** operator/capacity and exposed allocation, not the build-level `/spec/mode`. A hybrid build must still check its local component. Provider-operated shared or opaque capacity gives `skipped` for local sizing/support assertions; quota and service limits remain #5/#9 questions. A managed component with a user-chosen instance type is in scope. Missing operator, capacity or route evidence gives `unknown`, never an automatic skip. For a known applicable component, absent memory inputs give `unknown` under its constraint rather than making it non-applicable.

The component deployment object and configuration key are #81 proposals awaiting #40 versioning. v1's `hosting_type` and build-level mode cannot substitute for those distinctions. The ordinary two-GPU hybrid example must therefore run the local checks; an API-only route skips them. COMPUTE-05 is retired as a standalone group and contributes no extra outcome. Component mode and routing changes invalidate every affected group.

## COMPUTE-01: per-device memory feasibility

- Participating kinds, roles, and JSON pointers: model primary `/spec/min_weights_vram_gb`; model selection `/settings/precision`, context_policy selection `/settings/requested_context_tokens` and `/settings/reserved_output_tokens`; accelerator primary `/spec/vram_gb` and selection `/settings/device_count`; compute_profile `/spec/accelerator_ref`, `/spec/accelerator_count`, selection `/settings/instances`; inference_engine version; optional fine_tuned_model `/spec/adapter_only`. ResourceEstimate metrics `inference.estimated_required_vram_gb` and `inference.estimated_peak_per_device_vram_gb` are inputs from an external estimate, not catalog facts. #40 must confirm references to estimate results.
- Applicability condition: shared component applicability above; enabled model with a user-visible accelerator allocation. Pin model/engine/context/profile and per-rank inputs before deciding fit.
- Assertion and source evidence: compare each rank's memory requirement with its usable allocation in identical units. Formula, C11/C14/C15 and exact hardware C01–C09. This is the shared **memory-fit family** with #81 W-R6, including per-memory-pool co-residency under proposed CD-2; T1 supplies inputs rather than a duplicate fit rule. A proven resident-weight lower bound exceeding allocation gives `fail`. An estimate meeting the build's proposed `min_resource_confidence` decides on its **upper bound**: a straddling range gives `fail`, flagged **may not fit**, with the whole range and assumptions shown. This is a conservative screen decision, not proof of physical impossibility. If the upper bound fits, the memory screen can `pass` only for that scenario; runtime and SLO remain unverified. If confidence eligibility is absent or not met, return `unknown` for review; do not invent a default threshold.
- Fixed severity: `compute-01.constraint=error`, `compute-01.evidence=warning`, `compute-01.applicability=info`; an estimated screen never becomes a proven hardware failure.
- Missing-data behavior: `unknown`, never use zero for missing cache/runtime or assume VRAM pools. If free allocation is absent, report an advertised-capacity screen only, not final fit. Rules needing interval data cannot become final v1 rules until #40 chooses representation.
- Explanation and remediation: explain the largest per-rank term and scenario; reduce admitted context/concurrency, use a supported quantization with quality evidence, choose a larger allocation, or validate a sharding/offload plan. Recompute after changes.
- Dependency edges and affected consumers: model/context/adapter/workload/engine/topology → estimate → accelerator/profile fit; cyclic re-evaluation with #6/#7/#11; #9/#31/#39 consume the distinctions.
- Passing example (synthetic): known allocation48GB, conservative scenario upper25GB/rank and supported one-device plan → memory-screen constraint `pass/error`; does not prove SLO/runtime.
- Failing examples (synthetic): known80GB allocation, exact resident unsharded weights90GB → `fail/error` even before KV. Eligible estimated range45.556–51.25GB against48GB → `fail/error`, flagged may not fit with the range displayed. The latter is a disputed/conditional estimate, not a measured OOM.
- Unknown / non-applicable example: “7B”, INT4 label, unknown quant metadata or runtime memory → constraint `unknown/error` and evidence `unknown/warning`; hosted API only → constraint `skipped/error`, applicability `skipped/info`.
- Version and migration impact: conditional research rule; no imported v1 edit. Need interval/usable allocation/topology facts reviewed by #40. Pin estimator version and rerun when any participating version/settings change.

## COMPUTE-02: model, engine and accelerator backend intersection

- Participating kinds, roles, and JSON pointers: model primary `/spec/model_formats`, `/spec/supported_precisions`, `/spec/access_modes`; accelerator primary `/spec/backends`, `/spec/precisions`; inference_engine primary `/spec/backends`, `/spec/model_formats`, `/spec/supported_precisions`; selected model precision and exact artifact/quantization/engine versions. Architecture, OS/driver and quantization implementation currently require supporting note evidence.
- Applicability condition: shared component applicability above; the selected engine loads an inspectable artifact on the exposed allocation.
- Assertion and source evidence: require a documented joint path for format, architecture, dtype, quantization implementation, backend and hardware/driver. Nonempty array intersections are necessary, not sufficient. C01–C05/C12 establish hardware and **historical vLLM0.10.2** support claims; C20 separately checks v0.31.0. Consult [#11's current engine record](../inference-engine.md) for installation conflicts; never transfer a table entry across versions or treat independent arrays as their Cartesian product.
- Fixed severity: `compute-02.constraint=error`, `compute-02.evidence=warning`, `compute-02.applicability=info`.
- Missing-data behavior: apply the [adopted interim conflict order](../gpu-compute.md#owner-review-and-interim-evidence-policy) before deciding. Normalize units, scope to the selection, prefer the selected version/latest effective date, then fact-specific authority; equal-ranked numeric evidence uses spread and a conservative bound. `unknown` remains for no eligible evidence or equally ranked opposite yes/no claims. Explicit unsupported documentation, or omission from an exhaustively sourced complete list, gives `fail`; omission from an unmarked subset gives `unknown`. Retain superseded claims and the deciding step. A checked eligible versioned joint path can `pass`, labelled unverified until reproduced.
- Explanation and remediation: report which layer lacks support, exact version and primary source; change supported engine/backend/artifact, or obtain reproducible evidence. Do not infer compatibility from native arithmetic precision.
- Dependency edges and affected consumers: model ↔ engine ↔ accelerator; #6/#10/#11/#33/#40; recompute all three after any selection change, not a sequential blocker.
- Passing example (synthetic policy test): eligible selected-release documentation establishes the exact artifact/engine/driver/hardware tuple with matching format/dtype/backend → scoped joint-support constraint `pass/error`, evidence **unverified** until independently reproduced. An arbitrary intersection of independent lists does not satisfy this example.
- Failing example (documented historical claim, still pending central verification): vLLM0.10.2 + AMD GPU + AWQ; C12 explicitly lists unsupported. Proposed result `fail`, `error`; do not generalize to all future engines or all INT4 algorithms.
- Unknown / non-applicable example: generic FP8 model+MI300X with unspecified FP8 format/kernel → constraint `unknown/error`, evidence `unknown/warning`; API-only model → constraint `skipped/error`, applicability `skipped/info`.
- Version and migration impact: one shared **joint-support family** with ENGINE-02 and #81 D-R3 (its quantization case), also receiving T1-M1 inputs. Version-pin claims; CD-3's configuration key and CD-6 lineage are proposals, not new canonical v1 fields. No final ruleset is issued here.

## COMPUTE-03: KV memory demand

- Participating kinds, roles, and JSON pointers: context_policy `/settings/requested_context_tokens` and `/settings/reserved_output_tokens`; v1 workload `/spec/concurrency` (do not reinterpret as engine admission); accelerator allocation; engine version/cache implementation and launch-option admission limit; model cache geometry from artifact evidence. #81's proposed `peak_concurrency` describes requests-in-flight demand; it is not an imported v1 field.
- Applicability condition: shared component applicability above; full-attention decoder-only model using explicit resident KV. Other attention architectures need their own derivation.
- Assertion and source evidence: reserve prompt+output for every **admitted sequence** and round to real cache blocks; calculate keys+values using KV heads. Engine admission is separate from workload peak demand; use peak demand conservatively when the admission limit is unknown, recording that assumption. Beams and parallel samples count separately. C11/C14 plus C15 mechanisms and reproducible arithmetic script. Model context limits are checked once by `rule.model.context.fit` / #7's context policy, not duplicated here. The 2–4GiB runtime bracket is an unverified sensitivity assumption.
- Fixed severity: `compute-03.constraint=error`, `compute-03.evidence=warning`, `compute-03.applicability=info`.
- Missing-data behavior: unknown for missing geometry, cache dtype/layout, both admission and peak demand, or context; no automatic default from model family name. A wrong formula for MLA is not “close enough”.
- Explanation and remediation: show cache bytes/token, context and sequence count; lower budget/admission or use a supported cache strategy and re-estimate. A queue can wait without device KV, so do not multiply by every pending HTTP request.
- Dependency edges and affected consumers: #2/#6/#7/#10/#11/#16/#28; context and workload changes invalidate estimate. T3 retrieval/ACL and T4 memory semantics are not changed.
- Passing example (synthetic formula test): L28,Hkv4,D128,BF16KV,1sequence8192tokens →469,762,048cache bytes; correct calculation gives constraint `pass/error`, conditional on those assumptions.
- Failing example (synthetic arithmetic test): L28,Hkv4,D128,BF16KV,1 admitted sequence of8192tokens requires469,762,048cache bytes; a supplied estimate of234,881,024bytes that omits values fails this accounting constraint. A context-limit failure belongs to `rule.model.context.fit`, not this group.
- Unknown / non-applicable example: no KV-head count/cache architecture → constraint `unknown/error`, evidence `unknown/warning`; provider-managed opaque cache → constraint `skipped/error`, applicability `skipped/info`, with provider capacity unknown.
- Version and migration impact: #40 needs architecture/cache dtype/strategy metadata and estimation assumptions; preserve v1. #6/#7 approve context independently; current model main must not silently replace historical artifact settings.

## COMPUTE-04: multi-GPU allocation and count consistency

- Participating kinds, roles, and JSON pointers: accelerator selection `/settings/device_count`; compute_profile `/spec/accelerator_ref`, `/spec/accelerator_count` and selection `/settings/instances`; engine `/spec/supports_multi_gpu`; model version; ResourceEstimate per-device peak. Explicit TP/PP/DP/EP plan, node/fabric and KV partitioning are note inputs pending #40.
- Applicability condition: shared component applicability above; more than one selected device, multiple instances/replicas, or model requiring a partitioned placement.
- Assertion and source evidence: reconcile provisioned device inventory with the selected plan; compare max rank requirement to actual per-rank allocation. Dense-model DP replicates weights, TP/PP have distinct partitions and synchronization costs; current vLLM separately qualifies MoE layers across TP×DP (C15/C21). Physical link differs by variant (C01–C03). `supports_multi_gpu=true` alone cannot verify a particular plan.
- Fixed severity: `compute-04.constraint=error`, `compute-04.evidence=warning`, `compute-04.applicability=info`.
- Missing-data behavior: unknown; never total VRAM pooling by default. Missing selected engine support is not false by omission.
- Explanation and remediation: show devices per replica and replica count separately. Obtain an engine-supported plan, adequate interconnect and per-rank peak estimate; choose one host/device SKU if a multi-node path is unknown.
- Dependency edges and affected consumers: #9/#10/#11/#31/#39/#40; a profile or replica-count change invalidates sizing/cost assumptions. Training topology remains #31's separate task.
- Passing example (synthetic): two documented1-GPU profile instances, selected physical count2, and two independently resident dense-model DP replicas with adequate per-device allocation → inventory constraint `pass/error` only. This multiple-instance scope is applicable; it does not prove throughput scaling or latency.
- Failing example (synthetic): one instance with profile accelerator_count1 but selected plan requires2simultaneous physical GPUs →`fail`,`error`; buying2DP replicas does not fix2-wayTP for one model.
- Unknown / non-applicable example: two48GB GPUs,90GB estimated total, no per-rank plan → constraint `unknown/error`, evidence `unknown/warning`; one-device deployment with no parallelism question → constraint `skipped/error`, applicability `skipped/info`.
- Version and migration impact: #81's proposed `placement` carries TP/PP/DP/EP assignments; inventory and per-pool semantics require #40 review. No schema mutation or universal approved boolean.
