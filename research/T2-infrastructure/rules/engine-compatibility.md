# Proposed release-scoped inference-engine rules

Issue: #11 · Contract review: #40 · Status: owner-reviewed proposals; executable ruleset pending / unverified · Version: 0.3.0

Evidence IDs refer to [inference-engine.md](../inference-engine.md): vendor sources were accessed 2026-10-16; central owner review E27 was accessed 2026-10-17. These proposals follow [the shared template](../../../templates/rule-proposal.md) and incorporate the [#3/#40/#41 owner decisions on PR #75](https://github.com/Pick-Your-AI/pick-your-ai-research/pull/75#pullrequestreview-5550616927). Publisher documentation can decide a scoped constraint while evidence remains **unverified**; it does not independently reproduce a joint runtime. Every example below is a synthetic rule illustration. Outcomes `pass/fail/unknown/skipped` are distinct from severities `info/warning/error`.

Each group below proposes three separate rule clauses. Severity is fixed on each clause, as required by v1 `Ruleset`; a result never changes its rule's severity:

| Group | Constraint clause: `error` | Evidence clause: `warning` | Applicability diagnostic: `info` |
| --- | --- | --- | --- |
| ENGINE-01 | `engine-01.constraint` | `engine-01.evidence` | `engine-01.applicability` |
| ENGINE-02 | `engine-02.constraint` | `engine-02.evidence` | `engine-02.applicability` |
| ENGINE-03 | `engine-03.constraint` | `engine-03.evidence` | `engine-03.applicability` |
| ENGINE-04 | `engine-04.constraint` | `engine-04.evidence` | `engine-04.applicability` |

The constraint clause asserts the group's scoped compatibility requirement. Eligible, versioned documentation can return `pass/error`, with evidence labelled unverified until independently corroborated or reproduced. A documented contradiction or absence from a source-complete list returns proposed `fail/error`. Absence from an unmarked list is `unknown/error`. Apply E27's scope/version/authority conflict order before returning unknown; only missing eligible evidence or unresolved equally ranked opposite yes/no claims remain `unknown/error`. An evidenced non-applicable case returns `skipped/error`. `error` is a rule classification; it does not turn a passing result into a failure. Proposed `on_unknown: review` requires review rather than silently treating missing data as a failure or a pass.

The evidence clause separately checks whether eligible claim-level evidence for the applicable tuple exists: checked documentation returns `pass/warning` with evidence status unverified, and missing or unresolved conflicting evidence returns `unknown/warning`, with proposed `on_unknown: review`; non-applicable tuples return `skipped/warning`. The applicability diagnostic returns `pass/info` for known applicable scope, `skipped/info` for known non-applicable scope, and `unknown/info` for missing scope with proposed `on_unknown: defer`. It does not claim runtime support. These shared clause definitions inherit each group's pointers, applicability, evidence, remediation, dependencies, examples and migration scope below; they are research proposals, not an executable approved Ruleset. E27 defers collapse of evidence/applicability clauses to CD-1; fixed severities are retained here.

Applicability is per serving component, including a local runtime in a hybrid build; an adapter inherits its base model's deployment. A provider-operated shared or opaque route skips local engine checks, while a managed component with user-chosen runtime/instance is in scope. Missing scope is unknown. The richer component deployment and configuration key are #81/CD-3 proposals, not new frozen-v1 fields. ENGINE-02, COMPUTE-02 and #81 D-R3 are one joint-support family for central implementation; the legacy headings below describe its scoped cases, not independent final rule IDs.

## ENGINE-01: exact artifact loader and architecture

- Participating kinds, roles, and JSON pointers: primary `model` `/version`, `/spec/model_formats`; `inference_engine` `/version`, `/spec/model_formats`; optional `fine_tuned_model` `/spec/artifact_format`. Exact architecture/artifact revision and plugin/build versions remain note-only inputs.
- Applicability condition: enabled customer-controlled engine loads a local model artifact.
- Assertion and source evidence: require an evidenced loader and architecture path for the exact release/artifact. E03/E10 describe vLLM loaders and separate GGUF plugin; E13 establishes a complete **GGUF-only direct-loader format list** for llama.cpp v0.7.0. This completeness is scoped to loader formats, not architectures, quantizations or backends; all other surveyed lists remain unmarked. E20/E24 describe TGI's bounded optimized support and best-effort fallback. Eligible release-scoped documentation can decide a pass labelled unverified [E27].
- Severity: `engine-01.constraint` is always `error`; `engine-01.evidence` is always `warning`; `engine-01.applicability` is always `info`, under the separate clause definitions above.
- Missing-data behavior (`unknown`) and proposed policy: intersecting file-format lists alone cannot pass. Missing plugin/version, architecture support, conversion correctness or eligible evidence yields unknown. Absence from the scoped complete GGUF-only format list fails; absence from unmarked lists remains unknown unless eligible documentation explicitly excludes the selection.
- Explanation and remediation: name the mismatched layer; choose an evidenced loader/plugin or convert and validate the artifact with immutable lineage. A suffix rename is not conversion.
- Dependency edges and affected consumers: #6 ↔ #11 ↔ #33; #10/#37/#40/#42; selection changes invalidate the scoped result.
- Passing example: checked, eligible v0.7.0 documentation covers the selected GGUF architecture, loader and pinned build conditions: constraint `pass/error`, evidence check `pass/warning`, evidence status **unverified** until independently reproduced or corroborated.
- Failing example: directly feeding a Safetensors checkpoint to the documented GGUF-only llama.cpp loader gives proposed `fail/error`.
- Unknown / non-applicable example: vLLM v0.31.0 + GGUF with no plugin pin gives constraint `unknown/error` plus evidence `unknown/warning`; provider API with no local runtime gives constraint `skipped/error` plus applicability diagnostic `skipped/info` for the known API-only scope.
- Version and migration impact: no v1 mutation. Preserve exact support tuples, plugin revisions and saved-build loader contracts in a reviewed next-version design.

## ENGINE-02: joint backend and precision case of the shared support family

- Participating kinds, roles, and JSON pointers: engine `/spec/backends`, `/spec/supported_precisions`; accelerator `/spec/backends`, `/spec/precisions`; selected model/engine precision and quantization. Model architecture, kernel/driver and weight/activation/KV roles require note evidence.
- Applicability condition: selected hardware executes the model through the chosen release/build.
- Assertion and source evidence: reuse the joint-support family shared with [COMPUTE-02](compute-capacity.md) and #81 D-R3, keyed by the configuration tuple. Require joint release, architecture, quantization and device support; E05/E10/E15/E25 supply conditional requirements. Eligible versioned documentation can pass with evidence labelled unverified [E27]. For vLLM v0.31.0 on Volta (7.0), E05's explicit CUDA minimum 7.5 outranks E10's positive cells: the cells are superseded for this tuple and the constraint fails. This does not reinterpret historical v0.10.2 support.
- Severity: `engine-02.constraint` is always `error`; `engine-02.evidence` is always `warning`; `engine-02.applicability` is always `info`, under the separate clause definitions above.
- Missing-data behavior (`unknown`) and proposed policy: flat enum intersections are insufficient. An `other` enum or native INT4/FP8 capability cannot establish a particular kernel path. Normalize units/names, filter eligible scope, choose the specific version/effective date, and rank authority by fact type before declaring a conflict unresolved. A stated limitation beats a same-publisher capability listing; explicit unsupported documentation fails. Only no eligible evidence or equally ranked opposite yes/no claims remaining after E27's order yield unknown. Absence from unmarked lists remains unknown.
- Explanation and remediation: report exact precision role, scheme and device/build constraint; select an evidenced alternative or obtain a reproducible check. Capacity remains #10.
- Dependency edges and affected consumers: #6/#10/#11/#33/#37/#40; recompute the cycle without imposing a research delivery order.
- Passing example: eligible checked versioned documentation covers the exact artifact/backend/device/build tuple: constraint `pass/error`, evidence check `pass/warning`, evidence status **unverified**. Reproduction can upgrade evidence status without changing the documented constraint outcome.
- Failing examples: vLLM v0.31.0 on Volta 7.0 contradicts E05's minimum 7.5, so `fail/error` despite the superseded matrix cells [E27]. TGI v3.3.7 EXL2 with more than one shard also contradicts E25's documented restriction: proposed `fail/error`.
- Unknown / non-applicable example: “FP8 + AMD” without layout/kernel/driver gives constraint `unknown/error` plus evidence `unknown/warning`; opaque provider API GPU gives constraint `skipped/error` plus applicability diagnostic `skipped/info` for the known API-only scope.
- Version and migration impact: CD-3/CD-6 supply the shared configuration/artifact key; #40 implements one family with COMPUTE-02 and #81 D-R3, rather than duplicate final IDs. Maintain release-specific evidence; no global support boolean or new precision enum. Historical results do not apply automatically to current releases.

## ENGINE-03: adapter lineage and loading semantics

- Participating kinds, roles, and JSON pointers: `fine_tuned_model` `/spec/base_model_ref`, `/spec/artifact_format`, `/spec/adapter_only`; primary model ID/version; engine ID/version. Base revision/tokenizer, adapter method/rank/targets/layout and routing/composition are additional evidence inputs.
- Applicability condition: an enabled unmerged adapter is loaded, or a fine-tuned artifact is claimed portable to this engine.
- Assertion and source evidence: require immutable compatible base/tokenizer lineage and exact engine adapter-loading support. E09, E14 and E22 distinguish per-request routing, multi-adapter batching and simultaneous scales; these are different capabilities.
- Severity: `engine-03.constraint` is always `error`; `engine-03.evidence` is always `warning`; `engine-03.applicability` is always `info`, under the separate clause definitions above.
- Missing-data behavior (`unknown`) and proposed policy: no adapter support boolean inferred from Safetensors/GGUF alone. Provider-locked output, unknown base revision, or missing artifact identity stays unknown. `/spec/adapter_only` is optional in v1: absence does not mean merged weights and must not bypass adapter checks without separate artifact evidence.
- Explanation and remediation: obtain #33's artifact manifest, matching base/tokenizer and supported conversion/layout; treat merged weights as a full checkpoint and size them once.
- Dependency edges and affected consumers: #6/#10/#11/#30/#33/#37/#40. #33 owns artifact identity; #11 serving; #10 residency; #31 training.
- Passing example: an adapter pinned to the selected immutable base, validated on the exact engine/backend/loading mode, gives constraint `pass/error` and evidence check `pass/warning` for that loader path.
- Failing example: an adapter with an explicitly different required base/target tensor shape gives scoped `fail/error`.
- Unknown / non-applicable example: unpinned PEFT adapter conversion gives constraint `unknown/error` plus evidence `unknown/warning`; an evidenced merged checkpoint with `adapter_only=false` gives constraint `skipped/error` for unmerged-adapter loading and applicability diagnostic `skipped/info`, and still runs ENGINE-01/02. Omitted `adapter_only` without artifact evidence gives applicability `unknown/info`, not a merged-checkpoint assumption.
- Version and migration impact: #40 must review lineage/conditional-support fields. Preserve historical adapter semantics and do not reinterpret routing as composition.

## ENGINE-04: required API feature and request contract

- Participating kinds, roles, and JSON pointers: engine ID/version and optional `/spec/supports_tool_calling`; agent/RAG consumer selections. Structured-output needs come from workload `output_format` and build `output_enforcement` in the proposed #81 W-R1, as directed by E27. These are proposed contract inputs, not existing v1 JSON pointers. Endpoint, schema dialect, parser/template, tool mode, streaming/error/cancellation behavior supply implementation/consumer evidence.
- Applicability condition: workload `output_format` and build `output_enforcement` require structured output, or the application requires tools, streaming or an API feature on a particular endpoint. No structured-output requirement is invented from a framework name.
- Assertion and source evidence: match the actual request contract and release configuration; E06–E08/E14/E17/E18/E23 preserve limits. vLLM guided-field removal and parallel-call behavior differ across historical/current releases. “OpenAI-compatible” is not whole-API equivalence.
- Severity: `engine-04.constraint` is always `error`; `engine-04.evidence` is always `warning`; `engine-04.applicability` is always `info`, under the separate clause definitions above.
- Missing-data behavior (`unknown`) and proposed policy: omitted feature booleans, undisclosed managed versions or missing eligible request-contract evidence yield unknown; do not infer unsupported from omission. Until W-R1 inputs exist in a reviewed contract version, record them in the note and leave a missing requirement unknown rather than fabricate a v1 field. Consumer acceptance remains a separate handoff even when checked documentation decides a support constraint.
- Explanation and remediation: identify failing endpoint/field/parser/template/schema constraint; use a supported request contract or obtain consumer acceptance evidence in #25/#16/#37.
- Dependency edges and affected consumers: #7/#11/#16/#25/#27/#33/#37/#38/#40; tool execution/authorization and knowledge ACLs remain with their owners.
- Passing example: proposed W-R1 inputs require a supported schema mode, and eligible checked documentation covers the exact release/model/template/parser and required behavior: constraint `pass/error`, evidence check `pass/warning`, evidence status unverified. A later consumer-fixture run supplies independent evidence and handoff acceptance separately.
- Failing example: requiring legacy `guided_json` on vLLM v0.31.0 after documented removal gives proposed `fail/error`; migrate to release-supported fields.
- Unknown / non-applicable example: an undisclosed managed engine advertising generic chat compatibility gives constraint `unknown/error` plus evidence `unknown/warning`; application requiring none of this rule's features gives constraint `skipped/error` plus applicability diagnostic `skipped/info` for the evidenced consumer requirement set.
- Version and migration impact: retain request-contract versions and consumer evidence; invalidate only affected tuples after an engine/template/parser change. No approved runtime acceptance tests or new canonical feature fields are introduced here.
