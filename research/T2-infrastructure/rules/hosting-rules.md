# Proposed hosting compatibility rules

Issue: #9 · Contract review: #40 · Status: proposed / unverified · Version: 0.3.0

Evidence IDs refer to [hosting.md](../hosting.md), accessed 2026-10-16. These follow [the proposal template](../../../templates/rule-proposal.md). Documentation supports premises; no rule is an approved Ruleset or independently verified joint deployment. Examples are synthetic policy examples. Outcomes and severities are separate.

This revision applies [#3/#40/#41's scoped owner review of PR #75](https://github.com/Pick-Your-AI/pick-your-ai-research/pull/75#pullrequestreview-5550616927), reviewed at `9e66622a4b2698a9305274f05da9c15ae5d90b8c`, accessed 2026-10-17. Classify each component by runtime operator and capacity; do not gate on build-level `/spec/mode` or infer mode from `hosting_type` or billing. Hybrid builds retain each component's checks. Known non-applicable scope skips; missing scope is unknown. The #81 deployment object, CD-6 attachment semantics and CD-9 location mapping remain proposals for a versioned contract, not new v1 fields.

Eligible checked documentation may decide a support assertion while evidence stays **unverified** until independently corroborated/reproduced. Apply the adopted conflict order before returning unknown: normalize units/names, select eligible most-specific scope, selected version/latest effective date, then fact-specific authority. Publisher requirements outrank its capability lists, and billing/legal pages outrank overviews. Equal-ranked numbers retain median/spread and use the conservative value; equally ranked opposite yes/no claims or no eligible evidence remain unknown. Keep superseded claims and the deciding step. Version-pinned facts do not expire merely with time; mutable prices, regions, quotas and terms remain dated observations, with no TTL or bulk-reuse permission implied.

Each group below separates a constraint, an evidence diagnostic and an applicability diagnostic. Each has its own proposed rule ID and **fixed severity**, as required by v1; none changes severity when its outcome changes. A passing constraint with severity `error` does not constitute a failure; the evaluator can still emit a finding retaining that rule's severity. An unknown constraint is not a failure: the separate `warning` diagnostic explains the missing evidence. #40 still reviews the assertions and note-only inputs before adoption.

## t2-hosting-private-networking

- Participating kinds, roles, and JSON pointers: selected `hosting_platform` catalog `/spec/supports_private_networking`; hosting selection `/settings/network_isolation`; exact host version/service/region scope; proposed #81 workload `network` (not a v1 field).
- Applicability condition: enabled host selection requests `network_isolation=private`, **or** the workload requests `network=private_network` under proposed #81 W-R8. Air-gap remains W-R8's separate assessment. Until versioned inputs exist, keep their evidence in the research note rather than adding schema fields.
- Assertion and source evidence: require documented private-network capability for the scoped service. AWS VPC H15 and HF intra-region PrivateLink H14 support positive capability findings; neither proves a particular route, identity policy or full residency.
- Fixed rule/diagnostic clauses: `t2-hosting-private-networking` has severity `error` and tests the documented capability when private isolation is requested; `t2-hosting-private-networking-evidence` has severity `warning` and reports unresolved scoped capability evidence; `t2-hosting-private-networking-applicability` has severity `info`. Applicability is `pass` when either host or workload requests private networking, `skipped` when both are known not to request it, and `unknown` when neither is positive and a requirement is missing.
- Missing-data behavior (`unknown`) and proposed policy: omitted booleans are unknown, not false. `true` does not establish configured isolation or air-gapped operation.
- Explanation and remediation: name the service/region and missing capability/configuration; choose an evidenced private-capable host or obtain a deployment/network review in #37.
- Dependency edges and affected consumers: deployment mode ↔ host ↔ network plan; #3/#9/#27/#35/#37. No native blocker introduced.
- Passing example: a private request plus a scoped documented `true` gives constraint `pass` (fixed severity `error`); applicability is `pass/info` and the constraint does not fail. Network configuration still requires evidence.
- Failing example: private request plus explicitly evidenced `false` gives constraint `fail/error`.
- Unknown / non-applicable example: private request with absent capability evidence gives constraint `unknown` and evidence diagnostic `unknown/warning`. A public host selection plus private-network workload still applies. Skip only when neither host nor workload requests private networking and both are known; missing workload scope is unknown. An air-gap request remains W-R8's separate assessment.
- Version and migration impact: existing v1 pointers suffice for this narrow assertion; retain evidence scope and service version, invalidate on changes; no schema edit or final rule publication.

## t2-hosting-mounted-storage-locality

- Participating kinds, roles, and JSON pointers: `storage` `/spec/storage_type`, `/spec/region`, `/spec/hosting_ref`; `compute_profile` `/spec/region`, `/spec/hosting_ref`; selected IDs and v1 `build.links` with `relation=stored_in`. v1 links carry `relation` and `required`; CD-6 proposes mount-versus-fetch detail, and CD-9 proposes provider-location mapping.
- Applicability condition: an evidenced direct mount whose provider imposes placement constraints; an arbitrary remote object fetch does not establish this scope. A `stored_in` link alone does not prove direct mounting.
- Assertion and source evidence: provider-agnostic attachment rule, with Runpod H21 as one documented instance: location-constrained standard volumes and Secure Cloud Pod limitation. A single serverless volume constrains worker placement to its datacenter; multiple volumes do not imply replication. Do not transfer those Runpod restrictions to another provider without its own evidence. Retire the earlier provider-specific proposal ID `t2-hosting-runpod-volume-locality`; it is not a second rule.
- Fixed rule/diagnostic clauses: `t2-hosting-mounted-storage-locality` has severity `error` and tests the scoped direct-mount placement constraint; its `-evidence` clause has severity `warning` for unresolved mount/location evidence; its `-applicability` clause has severity `info`. Applicability is `pass` for a known relevant mount, `skipped` for remote-fetch-only scope and `unknown` if the relationship is missing.
- Missing-data behavior (`unknown`) and proposed policy: missing datacenter, cloud type, placement guarantee or mount relationship gives unknown. Provider geographies cannot be compared by arbitrary free text.
- Explanation and remediation: co-locate supported compute and storage, use an evidenced supported attachment strategy, or choose separate storage; preserve data consistency and capacity questions.
- Dependency edges and affected consumers: #9/#10/#13/#15/#27/#28/#31/#37; #13/#28 retain ACL, retention and memory semantics.
- Passing example: evidenced Secure Cloud Pod and directly mounted standard volume both in `US-KS-2` gives locality-only constraint `pass` (fixed severity `error`); applicability is `pass/info` and no failure diagnostic is emitted. Current GPU stock remains unknown.
- Failing example: direct mount of a single `US-KS-2` volume to a worker pinned in another datacenter gives proposed constraint `fail/error`.
- Unknown / non-applicable example: worker placement unspecified gives constraint `unknown` and evidence diagnostic `unknown/warning`; a remote download with no direct mount gives constraint `skipped` and applicability diagnostic `skipped/info` for this mount assertion.
- Version and migration impact: #40 must review explicit mount/placement semantics before implementation. Preserve v1; do not infer mount edges merely because components share a build.

## t2-hosting-offering-membership

- Participating kinds, roles, and JSON pointers: host `/spec/regions`, `/spec/accelerator_refs`; selected hosting `/settings/region`; profile `/spec/hosting_ref`, `/spec/region`, `/spec/accelerator_ref`. Evidence completeness/account entitlement remain note-only pending CD-3/CD-9. Residency policy is a separate #81 D-R6 check, not this offering assertion.
- Applicability condition: a particular region/device offering is being evaluated; API-only hidden hardware does not acquire a local device requirement.
- Assertion and source evidence: H02/H03/H05/H16/H18 show why region lists, price tables, quotas and current capacity are different facts. Positive scoped evidence can support an offering-presence assertion; a researched subset cannot establish absence.
- Fixed rule/diagnostic clauses: `t2-hosting-offering-membership` has severity `error` and tests scoped offering presence; `t2-hosting-offering-membership-evidence` has severity `warning` and reports incomplete offering/completeness evidence, with quota/stock uncertainty explicitly separate from offering presence; `t2-hosting-offering-membership-applicability` has severity `info`. Applicability is `pass` for a known explicit offering request and `unknown` for unspecified scope. Provider-owned hidden hardware skips only the **local accelerator** membership assertion; a requested API region still requires regional offering evidence.
- Missing-data behavior (`unknown`) and proposed policy: absent from an unmarked/incomplete list means unknown; absence from an exhaustively sourced complete list, or an explicit eligible unsupported statement, fails. Leave researched subsets unmarked. Published presence is not available quota, stock, a reserved allocation or permitted residency.
- Explanation and remediation: show requested location/device, evidence scope/date and unknown account capacity; obtain current authorized offer/quota evidence or select an evidenced alternative.
- Dependency edges and affected consumers: #3/#9/#10/#14/#15/#27/#31/#37/#39/#40; informational compatibility cycle, no delivery blocker.
- Passing example: a documented offering in the requested provider region gives offering-only constraint `pass` (fixed severity `error`); applicability is `pass/info` and no failure diagnostic is emitted. Stock remains separately unknown.
- Failing example: an authoritative exhaustive offering list excludes the selected location/device, giving scoped constraint `fail/error`. A prohibited jurisdiction is instead a D-R6 residency failure even if an offering exists there.
- Unknown / non-applicable example: the two-region researched host subset omits a third region, giving constraint `unknown` and evidence diagnostic `unknown/warning`; provider-owned API GPU selection gives constraint `skipped` and applicability diagnostic `skipped/info` for local accelerator membership.
- Version and migration impact: #40 must adopt evidence completeness and provider-location mapping before negative membership checks. No new enum, blanket compatibility boolean or schema change is made here.
