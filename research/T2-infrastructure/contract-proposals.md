# T2 contract and rule proposals for #40

Issue: [#40](https://github.com/Pick-Your-AI/pick-your-ai-research/issues/40) · Review owner: @tynamite · Status: proposed, unapproved · Contract baseline: 1.0.0 on `main`

No imported schema, generator, reference evaluator, baseline rule or canonical enum is changed by this research. The authoritative shapes remain [CatalogItem](../../contracts/v1/schemas/catalog-item.schema.json), [Pricebook](../../contracts/v1/schemas/pricebook.schema.json), [ResourceEstimate](../../contracts/v1/schemas/resource-estimate.schema.json) and the [component guide](../../contracts/v1/docs/COMPONENTS.md). The findings below are proposals with examples and consumers, not alternate JSON contracts.

Each proposal supplies participating fields, applicability, assertion/evidence, explanation/remediation, missing-data behavior and passing/failing/unknown/non-applicable examples. Outcomes are `pass`, `fail`, `unknown`, `skipped`; severities separately `info`, `warning`, `error`. Synthetic examples illustrate assertions only and are never vendor measurements. A sourced premise, a schema pass, an approved rule and a consuming-owner acceptance are separate milestones.

| T2-C06 multi-version intake and freshness policy | Intake permits one version per catalog ID, although engine behavior changes per release. Catalog `active` describes lifecycle and does not assert security currency. #41 has not adopted freshness thresholds or reuse rights. | Decide version-retention window, immutable snapshot membership and saved-build invalidation events with #41; define source-conflict precedence and what checked versus independently verified means. Historical matrices stay dated notes under the present intake. | #11/#8 @Mattycodes69; #41/#40/#42 @tynamite; all downstream owners | A next-version or intake-policy proposal needs unambiguous ID+version resolution and migration tests. Current submission retains one exact engine version per ID and does not claim a TTL or commercial reuse grant. |

The imported reference membership rules need special review: `precision.engine` and `engine.model.format` can hard-fail on omitted entries in a researched subset. This applies to engine format/backend/precision arrays as well as host lists. For example, a minimal vLLM dtype proposal omitting INT4 cannot become evidence that a documented INT4 scheme is unsupported. #40 must define completeness and scoped negative evidence or a conditional support lookup before executable consumption. This research does not alter the frozen baseline or certify it as suitable for these proposals.
