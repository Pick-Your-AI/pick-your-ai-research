## Current assembly and normalized-input contract

The context input `P` is the **actual complete model request**, after the selected serializer/chat template: system and developer content, role/template overhead, current user content, retained history/thinking, declared tools and schemas, tool results, retrieved content and citation metadata, memory, and applicable media. The output reservation `O` is generated output including any reasoning/thinking subset under that selected route's accounting. Do not add the same thinking allowance twice. Future tool results or later turns require their own eligible bounds or remain unresolved. Repeated content actually serialized twice counts twice; two labels for the same already included contribution do not create a second charge.

This reconciles [#16's context proposal](../T3-knowledge-retrieval/rag-retrieval.md), [M8 in #28](../T4-agents-integrations/agent-memory.md), and the current [CD-5 0.2 stage-workload proposal](../T0-configuration/workload-use-case.md#cd-5-per-stage-workload-candidate-2026-10-18). A stage's already complete input is not augmented again with its source objective, memory or RAG fields. Stage `mean` / `max` are workload statistics, **not automatically lower/upper uncertainty bounds**. Request counts, turns, retry assumptions and sibling-stage demand have distinct meanings; shared demand is not duplicated across stages without an explicit allocation/overlap assumption.

[CD-11's test-only candidate](../T0-configuration/component-schema-compatibility.md#cd-11-typed-context-and-exact-route-binding-candidate-2026-10-18) provides a bounded route/selection/tokenizer/settings identity and lower/upper context interface. Its normalized arithmetic is not a production source resolver or approval of a new wire format. Keep original Build and answer bytes, exact selection/item versions, source and association identities, tokenizer/template/processor configuration and uncertainty provenance. A model, route, operation, tokenizer, native-unit setting or Build revision change requires fresh scoped evidence/association; an old count cannot be relabelled current. Missing, unknown, withheld and not-applicable answers retain their different meanings. A known native limit or a known failure is not erased because another operand is unresolved. Final source resolution, field normalization, activation and successor migration stay with #40/#42.

### Counting and transformations

Use an eligible counter for the exact complete request when supported; retain that method's documented approximation and exclusions. For self-hosted text, pin the tokenizer artifact and chat template, thinking mode, generation prompt and special-token settings. Fragment totals do not automatically equal the fully serialized request, even with the same tokenizer. An upper bound needs an applicable derivation or calibration; a raw-string demonstration, `ceil(characters / 4)`, an unrelated encoder or an arbitrary multiplier supplies none. Native media measurements require the selected processor and unit semantics, not a text conversion.

RAG's chunk/header subtotal and M8's memory subtotal are component screens. They cannot establish complete CTX-01 fit, and an unevidenced zero header allowance is not measured zero. Embedding and reranking have their own selected models, tokenizers and input limits. A retrieval screen must retain source/citation identity and account for assembly overhead; final serialization and complete-request recount govern generation.

Any truncation or compaction must first have evidenced support and an explicitly allowed policy. #16 retains the proposed whole-chunk ranking/drop choice and citation handling; #28 retains required-memory preservation. Neither subsystem may independently spend the other's budget or silently discard required instructions/content. After an allowed transformation, preserve necessary content and references and recount the whole affected request. A summarizer/extractor call is a separate model request with its own limits and possible cost. Output reservation is not an extra memory allowance. Quality is a separate [W-R10/#36](../T0-configuration/workload-use-case.md) decision only when the user selects a quality target; neither token fit nor a transformation establishes that target.

## Token estimation method and uncertainty

The request-counting method remains proposed. A [bounded raw-text tokenizer study](token-estimation-study.md) now measures its text-only component on synthetic inputs; it is not a full request counter or runtime-admission measurement.

1. Freeze model/route and the full planned request. Include system/developer instructions, role/template markers, retained history/thinking, tools and their results, RAG and memory, media settings and the generation reserve. Count after assembly; recount after edits, compaction, tool rounds, model changes or tokenizer/template changes. Budget future tool results separately until their payloads exist.
2. Prefer the provider's supported request counter for that exact model/API. Claude accepts structured message inputs but currently rejects many server tools, MCP connector inputs and URL/file media sources; unsupported portions remain unknown (CW05). Gemini `count_tokens` counts input, not future generation (CW07). Bedrock advertises Count tokens support for the scoped 4.6 route (CW09); no call was made. OpenAI documents tiktoken-based string estimation (CW02); this note does not establish an exact GPT-5.4 tokenizer mapping or exact whole-request local count.
3. For Qwen, tokenize with the pinned repository's tokenizer and chat template, retaining `enable_thinking` and generation-prompt settings (CW11). Exactness applies to the resulting local token sequence only if the serving runtime uses that same serialization; it does not establish output length or quality.
4. If only text size is known, keep a rough estimate labelled **Estimate**, with tokenizer/language/modality assumptions. A characters-per-token heuristic is not a universal bound. Without calibration, report an unknown error bound and return `unknown` near any limit, not an asserted fit. Do not apply a text ratio to images, audio or video.
5. For a later authorized calibration, compare estimates with provider usage over representative languages, code, tool payloads and media settings. Record signed residuals (`actual - estimate`), sample count, minimum/maximum and empirical quantiles per stratum. Use an upper residual envelope only within the calibrated scope; distinguish an observed sample envelope from a confidence interval or guaranteed bound. Recalibrate after route/tokenizer changes. The linked local study records actual text-tokenization residuals only; no provider calibration or deployable numeric safety margin is established.
6. If valid lower/upper input bounds exist, decide conservatively on the upper bound: within every applicable budget is a scoped pass; exceeding any known cap is fail. When the interval straddles the cap, flag the fail **may not fit** and show the range, following the central owner's PR #88 review. This is an estimated screen, not a measured API rejection. With unbounded omitted content, fit is unknown. An unbounded point estimate can support a labelled planning scenario but never an unconditional pass.

For unknown long-context extension configuration, evaluate the limit predicate against the evidenced native limit. Qwen's 100,000-token request without YaRN evidence therefore fails its published native 32,768-token limit; evidence an extended configuration or reduce the request. Independent runtime/memory predicates can remain unknown for review. A native-limit pass never proves runtime support, memory fit or quality.

Thinking is part of generation reservation for the scoped Claude route (CW04). OpenAI includes reasoning in context (CW02). Do not add a reported output total and its reasoning subset again. Cached input may cost less but still occupies context. Reserve length is an admission/planning quantity, not a prediction of billed generated tokens.
