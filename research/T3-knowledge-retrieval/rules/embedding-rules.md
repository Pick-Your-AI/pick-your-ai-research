# Embedding rule proposals

Issue: #14 · Contract review: #40 · Status: proposed · Research rule revision: 0.2 · Source access date: 2026-10-18

These four proposals replace the compressed EMB-01–04 rows in [embedding-model.md](../embedding-model.md), with the same stable rule IDs. They use the [shared template](../../../templates/rule-proposal.md) and [decided #40 outcome semantics](../../T0-configuration/component-schema-compatibility.md#rule-format-and-outcome-semantics-decided). They are research policy, not an approved Ruleset, a schema migration or an executed backend test. E1–E7 refer to the dated primary sources in the parent note. Every example below is synthetic reasoning.

## Common identity, evidence and path scope

**Participants and pointers.** Resolve each participating selection by `/id`, `/kind`, `/role`, `/enabled`, `/catalog_item_id` and `/catalog_item_version`, with the referenced CatalogItem's `/id` and `/version`. The frozen [selection schema](../../../contracts/v1/schemas/selection.schema.json) supplies the settings named below. Catalog pointers refer to that selected CatalogItem, not to an arbitrary product with a similar name. Query/document profiles, index-generation identity and a complete retrieval-path binding have no complete adopted v1 shape. Their proposed types and required evidence are in the parent note's [profile dictionary](../embedding-model.md#representation-profile-and-index-generation-record); no fictional JSON pointers are assigned to them.

**Quantification and activation.** First perform canonical schema/reference validation and #40's whole-inventory identity preflight, including disabled and unrelated selections. Invalid or ambiguous identities are input errors, not `skipped` findings. Then evaluate every enabled relevant path, including non-primary RAG paths, vector-backed memory and retrieval exposed through a tool. A path names its actual query encoder, document encoder, selected index field/namespace and population generation, whether its implementation is bundled or separately selected. An absent `rag_pipeline` does not make a known tool or memory vector path inapplicable. This is a requested #40 binding, not a claim that the current prototype discovers these paths.

For a complete, valid scope, known required vector retrieval with no participating encoder/backend must fail the preceding required-presence check; unknown activation or an incomplete path inventory cannot prove absence or compatibility. Keep that result separate from the EMB predicate. Known disabled or wholly non-vector paths are inapplicable. Unknown applicability yields `unknown` without asserting compatibility. On applicable paths retain all findings: any failure makes the universal summary `fail`; otherwise an unresolved row makes it `unknown`; otherwise at least one applicable passing row permits `pass`; no applicable rows yields `skipped`. Empty optional scope is never a vacuous pass or a substitute for required presence. This follows the distinction between #40's [universal and required-presence modes](../../T0-configuration/component-schema-compatibility.md#cd-13-synthetic-selection-experiment-2026-10-18); it does not adopt their wire representation.

**Evidence and fixed policy.** Each rule has fixed severity `error` and `on_unknown: review`. Use eligible evidence for the actual version/configuration/condition; normalize and scope conflicting sources before applying #40/#41's authority and conservative-value order. Do not relabel every disagreement as unknown. An undocumented list omission is not a demonstrated incompatibility. A rule may pass on eligible publisher documentation while its evidence status remains `unverified`; no runtime execution is invented. A passing error-severity rule is not an error outcome. A representation result says nothing about authorization, residency, rights or measured retrieval quality, which retain their own rules.

## EMB-01: selected dense widths match

- **Participating kinds, roles, and JSON pointers:** each dense path's query/document `embedding_model` selections, their CatalogItems `/spec/embedding_dimensions` and selections `/settings/output_dimensions`; actual `vector_database` selection `/settings/index_dimension`. Roles and generation/field binding use the common envelope. A bundled backend must provide equivalent scoped evidence, not an invented separate selection.
- **Applicability condition:** the known selected retrieval representation is a single dense vector. Known sparse or multivector output is outside this scalar-width assertion; its representation-specific shape/operator obligation remains unresolved elsewhere and is not an overall compatibility pass.
- **Assertion and source evidence:** the actual selected query width, document width and target index-field width are equal positive integers. Resolve an explicit selected width first; use a published default only with evidence that the selected encoder configuration uses that default. E1 documents configurable output dimensions; E2/E3 document dense widths. The equality check and per-path binding are project policy inferred from the encoder/index boundary. Maximum backend/type/index capacity is the distinct VDB-01 check in [#15](../vector-database.md).
- **Severity:** `error`.
- **Missing-data behavior and proposed policy:** unknown actual width or field binding → `unknown`, `review`. A catalog default or `max_dimensions` value alone cannot fill missing selected-index evidence. Known unequal widths fail; missing evidence does not become zero.
- **Explanation and remediation:** identify the query, document and index field with their selected widths. Select supported equal widths and re-encode the affected population when needed, or choose a compatible field/backend. Lowering a query width alone does not resize already stored vectors. Check VDB-01 and EMB-02/03 separately.
- **Dependency edges and affected consumers:** #13 ingestion, #15 selected field and capacity, #16 query path, #28 memory index, #39 rebuild/storage quantity, #40 path/reference binding.
- **Passing example:** a synthetic dense path has query width 1,024, document width 1,024 and its selected field width 1,024, each supported by eligible configuration evidence. This rule passes even though the other rules still need evaluation.
- **Failing example:** a non-primary memory path has query/document width 1,024 and its own index field width 768. Another primary RAG field at 1,024 cannot rescue this failure.
- **Unknown / non-applicable example:** a configurable encoder has a catalog default but an unrecorded serving override → unknown. A known keyword-only path → skipped. A sparse path skips this scalar rule while retaining its separate shape check.
- **Version and migration impact:** retain `EMB-01`, proposed revision 0.2. Adopt path/field binding and selected-default evidence only through #40's versioned contract/ruleset process. Frozen `rule.embedding.dimension` and its historical outputs remain unchanged.

## EMB-02: query, document and index generation are bound

- **Participating kinds, roles, and JSON pointers:** common query/document `embedding_model` identities and selected output dimensions; selected `vector_database` `/settings/index_name` where supplied. Artifact/tokenizer/runtime/pooling/normalization/instruction profiles, compatible pair identity and generation-population provenance are conceptual operands, not new v1 fields. `knowledge_base`, `memory_store`, `rag_pipeline` or `tool` identifies the consuming path.
- **Applicability condition:** a known enabled vector retrieval path compares encoded queries with a populated document representation, including a memory retrieval index.
- **Assertion and source evidence:** the selected query profile is documented or independently evidenced as compatible with the document profile that actually produced this index generation. Bind task, modality, encoder artifacts or service routes, tokenizer, role-specific preprocessing, pooling, normalization and output configuration. The two roles need not have identical instructions: E3 requires different query/passage prefixes for asymmetric retrieval; E6 also separates query instructions from document encoding. E2's dense path is a different contract. Equal dimensions and a shared model-family label cannot prove compatibility. Requiring this generation/pair join is project policy; an explicitly evidenced compatible dual encoder or equivalent runtime implementation is allowed.
- **Severity:** `error`.
- **Missing-data behavior and proposed policy:** absent generation lineage, unresolved hosted snapshot/configuration or unknown pair compatibility → `unknown`, `review` for the affected assertion. Preserve every known alias, source date and profile field. A known incompatible pairing fails; a runtime version change alone triggers review but does not prove incompatibility.
- **Explanation and remediation:** display which query profile will search which document generation and why the pairing is eligible. Restore a compatible query profile, establish scoped equivalence, or build a new generation under an explicit migration plan. Do not silently repoint an old index name at new encodings or erase the prior profile.
- **Dependency edges and affected consumers:** #13 chunk/source lineage, #15 generation/namespace, #16 query preparation, #28 memory reuse, #9/#11 actual serving path, #39 migration quantities, #40 reference/version adoption, #36 quality evaluation.
- **Passing example:** an E3-style synthetic pair uses one pinned model/tokenizer, documented mean pooling/L2, `query: ` for a retrieval query and `passage: ` for the indexed documents; the generation record binds those profiles. Different legitimate role prefixes do not fail the pair.
- **Failing example:** both vectors have width 1,024, but the selected query uses a known incompatible encoder/profile while the stored generation was produced by another. A shared width cannot convert the known incompatibility to pass.
- **Unknown / non-applicable example:** an index records only a mutable service alias and no evidence establishing the relevant generation/pair identity → unknown. A known exact-key memory path without vector comparison → skipped.
- **Version and migration impact:** retain `EMB-02`, revision 0.2; replace the ambiguous earlier "same instructions" shortcut with a compatible role-pair requirement. Query/document/generation representation, link resolution and historical profile locks require #40 adoption; do not mutate frozen schemas or silently recompute historical findings with new source evidence.

## EMB-03: scoring and normalization are compatible

- **Participating kinds, roles, and JSON pointers:** paired `embedding_model` CatalogItems `/spec/similarity_metrics`; selected `vector_database` CatalogItem `/spec/supported_metrics` and selection `/settings/similarity_metric`; actual path binding. Normalization, operator, score transformation and ordering direction are conceptual evidence operands. Optional #16 thresholds are separate settings requiring their own representation.
- **Applicability condition:** a known enabled vector path ranks the selected representation using the selected index operator. A scalar metric name does not describe a complete sparse or late-interaction scoring function; evaluate such a path only with its appropriate complete scoring contract, otherwise keep the applicable assertion unknown.
- **Assertion and source evidence:** the actual index operation, normalization and direction implement the encoder pair's supported scoring contract. E2's dense example uses dot-product scoring; E3's documented path applies L2 normalization before dot product; E1 describes unit-normalized embedding rankings. For nonzero unit vectors, cosine equals dot product and squared Euclidean distance is `2 - 2 × dot`, so ascending distance gives the same ordering as descending similarity (mathematical identity, not a backend test). An operator may expose a sign change or distance transformation; preserve it instead of matching display strings only. Equivalent order does not establish equal returned scores, thresholds or approximate-index recall.
- **Severity:** `error`.
- **Missing-data behavior and proposed policy:** missing selected normalization/operator/direction evidence → `unknown`, `review`; an omission from a non-exhaustive supported-metric list remains unknown under #40/CD-3. A known incompatible operation fails. An eligible, exhaustive scoped list can establish an unsupported operation.
- **Explanation and remediation:** name the actual vector field, operator, normalization location and result ordering. Use a supported operation or an evidenced equivalent transformation; re-encode if normalization/profile changes require it. Validate threshold meaning and retrieval quality separately under #16/#36.
- **Dependency edges and affected consumers:** #15 backend/operator configuration, #16 score use and thresholds, #28 memory retrieval, #36 quality, #40 evidence/list completeness and operand adoption.
- **Passing example:** an E3-style unit-normalized pair is searched with supported dot-product similarity and descending ordering. The selected configuration evidence covers both roles and the actual index operation.
- **Failing example:** the declared retrieval contract requires descending similarity but the selected adapter knowingly returns the least similar values first. A different operation's "cosine" label cannot repair the reversed ranking.
- **Unknown / non-applicable example:** a product advertises cosine search but the selected adapter's normalization and returned ordering are unknown → unknown. A known keyword-only path → skipped.
- **Version and migration impact:** retain `EMB-03`, revision 0.2; keep frozen `rule.embedding.distance.support` unchanged. Additional operator/normalization fields and backend-specific conversion fixtures require #40 review. No threshold or quality winner is adopted here.

## EMB-04: input processing preserves the required content

- **Participating kinds, roles, and JSON pointers:** each applicable query/document `embedding_model` CatalogItem `/spec/max_input_tokens`; `knowledge_base` selection `/settings/chunk_size_tokens` and `/settings/chunk_overlap_tokens` when present. Selected tokenizer/revision, prefix/special-token accounting, item/request limits, truncation behavior and content-retention requirement are conceptual per-role operands. A memory/tool path may supply input without a `knowledge_base` selection.
- **Applicability condition:** an enabled path encodes query or document input and has an applicable input-processing requirement. Evaluate each role and encoding stage; a query against an existing index still has input limits even when no document ingestion occurs in that request. Unknown content-retention need is not treated as permission to drop content.
- **Assertion and source evidence:** the complete encoded input follows the selected role's documented preparation, satisfies the selected item and aggregate request limits, and retains the content required by the declared policy. Count instruction/prefix and special tokens with the actual embedding tokenizer. E3's example truncates at its configured input length; E4 separately specifies per-item and per-request bounds. The requirement to prevent unacknowledged content loss is project policy. An explicitly accepted lossy policy can be evaluated as such; it must not be labeled full-content preservation.
- **Severity:** `error`.
- **Missing-data behavior and proposed policy:** missing tokenizer, selected limit, truncation behavior or applicable content-loss requirement → `unknown`, `review`. Known oversized input that violates the required preparation, or known unacknowledged truncation under a full-content requirement, fails. Unknown billed units remain a separate #39 uncertainty.
- **Explanation and remediation:** report the applicable role, complete token count and item/request boundary, with the declared content policy. Re-chunk, reduce the input while preserving its required content, or obtain an explicit lossy-policy decision. Splitting a request can fix its total size but cannot fix an oversized item. Recompute the generation prompt with its own tokenizer under #7/#16; embedding counts cannot certify generation-context fit.
- **Dependency edges and affected consumers:** #13 chunking/lineage, #16 query and final-prompt assembly, #28 memory extraction/retrieval, #39 encoding quantities, #40 field/answer adoption, #36 completeness/quality tests.
- **Passing example:** a synthetic prefixed E3-style input totals 500 tokens including special tokens under an evidenced 512-token selected limit; no required content is dropped, and the request also satisfies its separate aggregate policy.
- **Failing example:** a complete synthetic input is 513 tokens and the selected service truncates it to 512 despite a full-content requirement. A returned 1,024-dimensional vector is not evidence that the lost content was preserved. Separately, E4's published request envelope rejects the synthetic `40 × 8,000 = 320,000` token batch even though its items fit individually.
- **Unknown / non-applicable example:** chunk size was counted only with the generation tokenizer, or truncation behavior is unrecorded → unknown. A known path that performs no embedding encoding → skipped.
- **Disputed evidence example:** two explicitly synthetic, eligible publisher observations remain equally ranked after normalization, scope, version/date and authority checks. They describe the same query role, tokenizer, route, version and selected configuration but give item limits of 500 and 512 tokens. The complete input is 508 tokens, including its instructions and special tokens, and the full-content requirement is known. Apply the conservative limit of 500: `508 > 500`, so the outcome is `fail`, flagged `disputed`, with fixed severity `error` and source-checked / unverified evidence. Preserve both observations and the conflicting limits. This is neither an unknown outcome nor a measured vendor limit; differently scoped or better-ranked evidence must be resolved before this equal-rank case applies.
- **Version and migration impact:** retain `EMB-04`, revision 0.2; clarify both query and document stages and conditional content-retention policy. A new tokenizer/profile or chunk plan may require a new index generation and re-costing. Input-policy, selected-limit and lineage operands require #40's versioned adoption; no arbitrary v1 extension, service retry behavior or implicit truncation default is added.

## Receiving and implementation boundary

The [parent handoff packet](../embedding-model.md#concrete-receiving-packet-and-completion-boundary) asks #13/#15/#16/#28/#39/#40 to review their exact interfaces. The rules neither choose a vector database nor replace VDB-01 capacity, VDB-02 action authorization, RAG-02 exposure controls, memory lifecycle policy or #36 evaluation. All known and unknown path findings must survive into any proposed result representation; a passing scalar rule is never a blanket "compatible" verdict. Source-reviewed research and actual native/runtime execution remain separate evidence classes.
