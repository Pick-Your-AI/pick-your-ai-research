## User decision

Which safety, security, and policy controls should this build include, and what does the builder show when one is missing?

The builder answers this per build. The answer depends on which optional workstreams are active (T3 retrieval, T4 tools and agents), the deployment mode chosen in T0 (API, managed, self-hosted), and the data sensitivity declared in T0 (#2). Whether a control works is evaluation (#36), not this record.

Mode labels follow [merged #81](../T0-configuration/deployment-mode.md): classify each serving control by its operator and capacity. Provider-operated shared moderation/guardrail endpoints are API; dedicated or reserved serving is managed; user-operated engines are self-hosted. Cloud provider name and desktop/CLI form alone do not decide the mode.

## Compatibility proposals

**Source checked** means checked against primary documentation, not independently reproduced.

**Rule interpretation (candidate revision 0.2).** Each row has one fixed v1 severity (`error`, `warning` or `info`), separate from outcome (`pass`, `fail`, `unknown`, `skipped`). The condition describes the violation: known applicable violation is `fail`; known absence of that violation is `pass`; non-applicability is `skipped` with `not_applicable`; missing eligible inputs are `unknown` with `missing_evidence` and `on_unknown: review`. Resolve conflicts using #41's scope, version/date and authority order before taking the conservative equal-rank numeric value, flagged disputed. Only missing eligible evidence or genuine unresolved ties yield `unknown`; conflict alone does not. Hypotheses remain unaccepted and cannot drive production verdicts. Suffixed rows split the old condition; the unsuffixed ID is retained for its stated scope. No frozen schema or executable ruleset changes. See merged [T0 modes and evidence policy](../T0-configuration/deployment-mode.md), [#126 rule review](https://github.com/Pick-Your-AI/pick-your-ai-research/pull/126) and [#127 evidence review](https://github.com/Pick-Your-AI/pick-your-ai-research/pull/127); both PRs are merged partial decision records. Their scoped owner decisions apply, while open #40/#41 acceptance and next-version adoption remain separate.

Format from #40: participants, condition, severity, explanation, suggested correction, source, rule version. Severity values: error, warning, info. Outcomes are separately pass, fail, unknown or skipped. Candidate revision 0.2 applies below.

## Recommendation and rationale

**Baseline for every build, independent of T3 and T4.** harm-classification-input and harm-classification-output (in API mode the provider often supplies the classifier, but OpenAI Moderation, Azure standalone and Mistral Moderation only flag, so the build still needs an enforcement step); system-prompt-no-secrets; zero-trust-output-handling; provider-retention-mode and data-residency-pinning declared against the T0 sensitivity; trace-content-masking whenever logging captures content; operator-stop-and-disengage; guardrail-failure-mode declared for every guardrail in the build.

**When T3 retrieval is active.** untrusted-content-segregation and tool-output-injection-screen on retrieved content; prompt-injection-detection that scans documents, not only the user prompt (Azure Prompt Shields documents field, Prompt Guard 2 on retrieved text); rag-store-access-control with a hard tenant boundary when more than one tenant shares the store; grounding-check where the workload needs cited answers.

**When T4 tools or agents are active.** tool-allowlist; destructive-tool-denylist; hitl-tool-approval for any tool that writes, sends, pays or deletes; consequential-action-confirmation for computer-use and browser tools; strict-tool-schema-validation; tool-choice-constraint on gated turns; least-privilege-credentials; sandboxed-code-execution with sandbox-egress-control and sandbox-lifetime-and-resource-limits for any code tool; mcp-oauth-audience-binding for remote MCP servers and mcp-local-server-install-consent for local ones; mcp-annotation-trust-policy; tool-audit-logging.

**What differs by mode.** In API mode the provider's classifiers are present whether or not the build wants them (Gemini defaults differ by version; Claude refusals cannot be disabled), and the operator's work is retention, residency and an external enforcement layer. In managed mode the platform supplies configurable blocking guardrails (Bedrock Guardrails, Foundry guardrails, Model Armor) and retention modes, so the operator's work is choosing the mode, the region and the exemption paperwork. In self-hosted mode every control is the operator's: classifier models need a GPU budget in T2 (G-R10), engines need telemetry opt-outs and egress policy (G-R25, G-R26), and licences on guard weights carry obligations (G-R11).

**Why a catalog and rules rather than a recommended product.** The sources show that no single product covers the catalog: harm classifiers lack injection and PII (G-R18), tool-policy engines are scarce (NeMo IORails is experimental and provider-limited, Invariant's maintenance is uncertain, Lakera and LiteLLM carry it as paid or gateway features), and data-boundary controls live in provider settings rather than guardrail products. The builder's job is to show which controls a selection leaves uncovered.

### What the builder shows when a control is missing

1. A missing control is a **rule result**, not a hidden default. It appears in the build's risk review with its severity, the rule's explanation and the suggested correction.
2. A failed rule with fixed `warning` severity can be **accepted** with a one-line reason stored in the saved build (#42). A `fail` result on a rule with fixed `error` severity cannot be accepted; the build stays marked not ready until the selection changes. A passing `error` rule does not block readiness.
3. `unknown` is shown as unknown with the open question and its owner, never as a pass. G-R8 (undocumented sandbox isolation) and the undocumented failure modes in guardrail-failure-mode are the first cases.
4. Controls the platform supplies in API or managed mode appear as **provided by platform** with the source, so the user can see what they rely on and what they cannot switch off (G-R19).
5. Severity is shown by label and icon, not colour alone.
