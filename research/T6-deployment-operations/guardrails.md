## User decision

Which safety, security and policy controls should this build include, which actual paths do they cover, and what should the builder report when a required control or its evidence is missing?

**Decision.** Keep a control catalog with explicit applicability, followed by selected-implementation checks. Choose controls from the workload's declared requirements and actual data/action paths. An application-owned enforcement boundary can qualify without a separate `guardrail` selection. Conversely, selecting a product, a framework or a `guardrail` item supplies no evidence that every required input, output, tool action or retained copy is covered. The [accepted W-R4 disposition](https://github.com/Pick-Your-AI/pick-your-ai-research/issues/2#issuecomment-6245701804) remains a `warning` recommendation; this note does not convert it into a universal production `error` gate.

**Engineering policy, separate from vendor facts.** Keep secrets and authorization outside model instructions; authorize the actual principal/resource/action before its side effect or earliest unauthorized data exposure; validate external content and model-derived arguments at their real boundary; make every selected control's action and no-verdict behavior explicit. Recommend human review for consequential or insufficiently trusted actions, with an approval scoped to the actual action, arguments, authority and current tool definition. Previously granted authorization may remain valid within its recorded scope. A model-generated call, schema match or general approval of another executor is not that authorization. These are project design decisions informed by E1–E6 and the accepted T3/T4 interfaces, not statements that a vendor enforces them or that all workloads have the same legal duties.

Mode follows the accepted [operator/capacity definition](../T0-configuration/deployment-mode.md): a provider-operated shared serving endpoint is API, dedicated or reserved provider serving is managed, and a user-operated serving engine is self-hosted. Control ownership, client location, wire transport and serving mode are separate dimensions. A local stdio MCP client may be part of an API build; a cloud guardrail or deployment object does not by itself make that build managed. All actual data destinations, including training, logging and recovery copies, remain in D-R6 residency and W-R8/CD-4 containment scope even when they do not decide serving mode. See the accepted [selected-offering deployment correction](deployment.md#selected-offering-applicability-recheck--2026-10-18).

**What this decision proves.** Primary documentation can establish a mechanism's bounded availability or documented behavior. An installation/configuration readback, a controlled enforcement observation and an effectiveness evaluation establish different facts. None inherits the others. [#36](evaluation.md) owns representative safety, quality and regression evidence; [#37](deployment.md) owns selected-target readiness; [#38](monitoring.md) owns operating signals. This record specifies their input contract, not their execution results.

### Evaluation and representation rules

**Whole-build binding first.** Validate identity, type, role, enabled selections and the actual implementation/resource associations before an applicability shortcut. Then evaluate every independently applicable control on every enabled actual path. One qualifying implementation can satisfy an existential requirement for its stated scope; it does not waive another enabled path’s authorization, lifecycle, telemetry or compatibility checks. A complete inventory can establish that an optional path is absent; a missing `guardrail`, `memory_store` or `rag_pipeline` catalog label cannot establish that by itself. The currently accepted RAG consumer still requires a bound pipeline for its existing rules until #40 adopts actual-path binding; this proposal does not bypass that gate.

**Applicability and outcome.** Each current G-R row below states a positive assertion and its separate applicability, using CD-1's compatibility terminal policy even when its fixed severity is `warning`. Preserve that severity and `on_unknown: review`; W-R4 retains its separately owned recommendation policy. Known false applicability is `skipped/applicability_false`; an explicit not-applicable answer is `skipped/answer_not_applicable`; missing/unknown/withheld applicability is `unknown` with its corresponding answer reason. A provided but unresolved predicate stays `unknown/predicate_unknown`. Only provided, known-true applicability evaluates the assertion; an unknown assertion remains unknown even for an applicable recommendation. Translate any retained violation-oriented source predicate through typed negation before terminal evaluation. A known violation gives `fail`; known satisfaction gives `pass`. `provided(false)`, `provided([])` and `provided(0)` remain provided values, not unresolved or automatically false predicates. The current typed `AnswerRule`/`PredicateResult` terminal path preserves responsible position/state/source path and lazy evaluation; the older Boolean sidecar loses those distinctions and cannot certify this envelope.

**Qualified sets and no false absence.** CD-3 positive support can witness `ANY` without exhaustive support or a complete set of unresolved alternatives. A qualified explicit exclusion, or absence of a known required member from an exhaustive applicable support inventory, can falsify `ALL` despite other unresolved requested members. Passing `ALL` or disproving `ANY` needs complete requested membership. Unmarked omission, a catalog boolean, empty search results or an unqualified support table is not negative evidence. A genuinely empty required set does not manufacture a compatibility pass; return the current `requirement_empty` unknown unless separately established non-applicability applies. Select eligibility by the exact tuple and operation; do not join independently supported columns into an unsupported combination.

**Keep claims separate.** A documented capability pass is not an observed-enforcement pass, and neither is an effectiveness score. A definitive applicable failure remains visible when unrelated inputs are unknown. Preserve all per-path results and their evidence reasons; do not hide a failure by taking an average or a convenient passing primary selection. Unknown service behavior remains unknown; the project's choice to hold a protected effect on no verdict is a policy requirement, not a fabricated vendor behavior. Readiness consumes the actual fixed rule/outcome pair plus independent deployment/evaluation evidence; a waiver or saved explanation never rewrites the result, source evidence or an unknown-policy block.

**Frozen mapping.** `guardrail` retains its existing required `/spec/targets`, `/spec/policies` and `/spec/enforcement`; targets use `input/output/retrieval/tool/training`, policies use the existing v1 enum, and enforcement uses `audit/block/redact/escalate`. The richer research taxonomy, selected/control inventories, action/authority binding, per-producer/layer evidence and typed reasons cannot be invented as additional properties in that closed schema. A category mapping requires an explicit per-control proposal; e.g. tool permissions can map to `tool_permissions`, while a CMK or approval record is not made complete by calling it `content`. No CatalogItem, Pricebook, Ruleset, schema or executable evaluator is adopted here. #40 must version an actual representation and migration with its affected consumers; #42 retains private answers and old result/source identities until that adoption.

## Recommendation, policy and missing-control display

Use the following **editable project baseline**, not a universal legal or vendor guarantee. For all builds, determine applicable input/output hazards, keep secrets and permission enforcement outside instructions, protect the actual output sinks, declare retention/residency and no-verdict behavior, and retain an operator stop/escalation path appropriate to the effects. Record content capture as off unless explicitly justified and authorized. This does not require every build to buy a classifier or add a `guardrail` catalog item.

For retrieval, keep trusted source/action authorization before the earliest unauthorized model/reranker/tool exposure, segregate external content and screen the actual surfaces required by policy. The accepted pre-generation and tool paths retain CTX-01 full assembled-input accounting after transformations and at each round. A selected grounding metric cannot substitute for access control or required cited-answer quality. An actual vector-free path may exist, but a missing catalog selection does not prove the complete path is vector-free; the existing bound-rag_pipeline gate remains in force until versioned adoption.

For tools/agents, minimize exposed and executable capabilities, bind approval to consequential or insufficiently trusted effects, validate final arguments, and apply actual principal/resource permissions. The configured gate must cover batching, parallel calls, delegation, retries and resumed/sticky approvals. HTTP MCP authorization and local stdio launch ownership follow #27; provider-hosted clients are execution paths, not a transport category. A completed action is not reversed by a later classifier refusal. Code execution needs a qualified isolation/egress/resource boundary, without inferring that all sandboxes or CPU/GPU choices behave alike.

For memory and retained data, keep the current W-R11 active-implementation declaration recommendation separate from M1’s qualified recovery check. A declaration pass supplies no recovery evidence and clears no M1 failure or unknown. Apply M2 storage, M3 adapter and M4 purpose/opt-in/action authority independently. The project's optional-memory opt-in default is not a universal legal consent requirement. M5/M6 and the retained G-H-MEM-01 packet use the complete actual event/configuration/layer inventory. Acknowledgement, tombstone, sampled disappearance, current serving exclusion, backup expiry and whole-policy completion are distinct. Known stale serving content fails even when another layer is unknown; non-serving backups retain their actual pending/permitted-retention status, and recovery must reconcile revocation before exposure. Application/framework-owned memory can qualify without inventing a `memory_store` selection. The retained CMK packet remains an exact resource/key/lifecycle requirement, not a provider-brand shortcut.

API, managed and self-hosted paths differ in who can configure and observe each control, not in whether data/action requirements disappear. An API build can have a platform guardrail/deployment object, local tools and private observations; a user-operated guard can wrap a provider model. Document the actual operator, capacity, route and responsibility for each control. Unavailable knobs or unobserved settings remain visible, rather than “provided by platform” becoming an enforcement pass.

The builder should show each scoped result with control/rule/version, affected implementation, fixed severity, outcome, evidence reason, required correction and follow-up owner. Display `unknown` for missing/withheld/unqualified evidence, separate from a known detector rejection, service error or unevaluated surface. Distinguish “documented available,” “configured/read back” and “observed under this test/window”; none means “safe” or “complete” without its stated evidence. A warning acknowledgement is a private saved decision with scope/version/reason; it preserves the warning/failure and does not change sources or waive a separate error/unknown-policy block. Passing an error-severity assertion is not a readiness block. Show labels and text, not color alone. #42’s accepted version/privacy mechanics govern persistence when an actual successor representation is adopted.

### Dated primary-source examples

All three sources were read **2026-10-18**, are mutable publisher documentation,
and are **source checked / unverified**. These are scoped documentary facts, not
observed account state, source-use grants or certifications.

- **Microsoft Azure AI Search:** [CMK guide](https://learn.microsoft.com/en-us/azure/search/search-security-manage-encryption-keys)
  distinguishes object binding from service-level defaults. Service-level CMK is
  preview (`2026-03-01-preview` management API); defaults protect new objects,
  not pre-existing ones. Inspection of inherited keys uses data-plane
  `2026-05-01-preview` or later. The guide requires service access to the key and
  distinguishes configuration readback, operational checks and resource-log
  evidence. Its cache-duration wording is inconsistent: some sections say up
  to **60 minutes**, while the rotation section also says **up to several hours**.
  Neither establishes a verified revocation deadline here. Rotation changes must
  propagate before old dependencies are removed. This is
  at-rest protection, not protection of data in use. Do not infer whole-service
  coverage from a default key or immediate revocation from a configuration change.
- **AWS KMS state:** [key-state documentation](https://docs.aws.amazon.com/kms/latest/developerguide/key-state.html)
  distinguishes Enabled, Disabled, PendingDeletion and other states. DescribeKey
  may succeed when cryptographic operations cannot. For custom key stores,
  disabling/deleting the backing key can cause cryptographic failure without
  changing the KMS key state. Thus an Enabled label alone is not end-to-end
  evidence that a selected storage service can use the key.
- **AWS KMS authorization:** [key-policy documentation](https://docs.aws.amazon.com/kms/latest/developerguide/key-policies.html)
  makes access dependent on applicable key/IAM/grant permissions and absence of
  denial. IAM allow statements need the key policy to enable their use; key
  policies are regional. A key identifier or permission in a different region
  is not an applicable authorization result.
