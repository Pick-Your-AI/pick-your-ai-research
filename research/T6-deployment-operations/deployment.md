## User decision

What does it take to ship this build, and is it ready?

In scope: packaging and configuration by deployment mode; rollout, rollback, secrets and access control; readiness checks. Out of scope: generating deployable artifacts.

Inputs. The Guardrails record ([#35](guardrails.md)) and the Evaluation record ([#36](evaluation.md)) sit in this folder and are cited here by control id (for example `least-privilege-credentials`), rule id (`G-R3`, `E-R18`) and gate id (`G1` to `G12`, with the meanings in the #36 gate table). The other information inputs (#3, #5, #9, #11, #13, #25, #27) were not available in this workspace. Where a step needs a T0 field those records have not defined yet, the step says so and the Open questions table names the owner.

### Mode definitions used in this record

Mode follows the serving-component decision in [T0](../T0-configuration/deployment-mode.md), merged through #81: user-operated serving is `self_hosted`; provider-operated dedicated or reserved capacity is `managed`; provider-operated shared capacity is `api`. Billing units and customer-owned deployment objects do not determine mode. Hyperscaler on-demand/shared inference is `api`; dedicated endpoints and provisioned throughput are `managed`. Training runs do not set serving mode. Select the actual offering/capacity rather than inferring a mode from the provider name.

Provider/platform labels in the source inventory are not mode decisions. Shared Azure Standard/Global/Data Zone token-serving routes are `api`; dedicated/reserved offerings are `managed`. For services with several configurations, record the selected capacity.


### Rollout gates: the scope decision #36 asked for

#36 flagged shadow, canary, A/B and rollback criteria to this record. Decision: the rollout mechanics (which unit is rolled out, how traffic is split, what must exist before traffic moves, how rollback is executed and what cannot be rolled back) are deployment steps here (S13, S25, S35, S36, S49, S50). The promotion criteria stay where they are measured: the quality metrics with #36 (G2 regression, G3 judge validity, G4 workload quality) and the thresholds and alert routing with #38. Shadow traffic (mirroring) has several opened sources (Azure ML managed online endpoints mirror up to 50 percent of traffic, D-M5; Flagger Blue/Green mirroring, D-O2; Microsoft's advice to use shadow or mirror mode when a canary is not possible, D-O14; the Azure Well-Architected operations page, D-D5), but none states a rule or a procedure for mirroring hosted APIs or prompts, so it appears only as hypothesis D-H9.

### Three findings that shape the record

1. No opened page maps deployment steps to deployment modes. The checklist is assembled from provider and project pages one platform at a time. "Source checked" on a step means an opened page states that step for that platform; no page states the checklist.
2. No number in this record is measured. Numbers are published with their source, labelled estimated where the record derives them, or builder-set. The checks that need a user-run measurement before the builder can show a result are: cold-start and weight-load time, rollback duration, SDK prompt-cache delay, GPU memory at the target context length and concurrency, and uncompressed image size. The rollback window is builder-set; the one published figure is advisory (D-O14: embedded teams "typically want about 30 days"). Absolute prices are deferred to #39. Two kinds of price data stay here because they change a decision in this record: published residency multipliers (D-A6, D-A7, D-A15; used in S17 and D-R9) and one published list price (NIM AI Enterprise, D-S19; used in the self-hosted licence decision).
3. Retirement is the highest-signal readiness check and the dates are close to the access date. claude-sonnet-4-5-20250929 retires on 2026-11-30 on the Claude API and reaches end of life on Bedrock on 2027-04-08 (D-A2, D-A35); Vertex lists Gemini 2.5 Pro, Flash and Flash-Lite for 2026-10-20 (D-A22), while the Gemini API deprecations page lists "No shutdown date announced" for the same three models (D-A19, updated 2026-10-12); other dates were seen in search snippets and are not used; OpenAI lists shutdowns on 2026-10-23, 2026-12-01, 2026-12-11, 2027-01-06, 2027-01-14, 2027-01-20, 2027-02-26 and 2027-04-01 (D-A14). Alias and auto-upgrade paths repoint a build without a code change on Gemini `-latest`, Mistral `-latest`, and Azure Standard deployments with an upgrade option (D-A19, D-A25, D-A31). OpenAI pages advise pinning a snapshot (D-P21, D-N301, D-N302) but do not say that bare names move, so that case is hypothesis D-H24; every Claude model ID is a pinned snapshot, while the pre-4.6 short aliases move (D-A1).

## Compatibility proposals

**Source checked** means checked against primary documentation, not independently reproduced.

**Rule interpretation (candidate revision 0.2).** Each row has one fixed v1 severity (`error`, `warning` or `info`), separate from outcome (`pass`, `fail`, `unknown`, `skipped`). The condition describes the violation: known applicable violation is `fail`; known absence of that violation is `pass`; non-applicability is `skipped` with `not_applicable`; missing eligible inputs are `unknown` with `missing_evidence` and `on_unknown: review`. Resolve conflicts using #41's scope, version/date and authority order before taking the conservative equal-rank numeric value, flagged disputed. Only missing eligible evidence or genuine unresolved ties yield `unknown`; conflict alone does not. Hypotheses remain unaccepted and cannot drive production verdicts. Suffixed rows split the old condition; the unsuffixed ID is retained for its stated scope. No frozen schema or executable ruleset changes. See merged [T0 modes and evidence policy](../T0-configuration/deployment-mode.md), [#126 rule review](https://github.com/Pick-Your-AI/pick-your-ai-research/pull/126) and [#127 evidence review](https://github.com/Pick-Your-AI/pick-your-ai-research/pull/127); both PRs are merged partial decision records. Their scoped owner decisions apply, while open #40/#41 acceptance and next-version adoption remain separate.

Shared #40 format, candidate rule revision 0.2. Source-checked rules have an opened page that states the condition. Hypotheses carry what is known and what would verify them. A failed rule with fixed `warning` severity can be accepted with a recorded reason. A `fail` outcome on a rule with fixed `error` severity blocks readiness; a passing `error` rule does not (the #35 convention). ## Recommendation and rationale

**Order of work.** Settle T0 first (S1), then terms and identity (S3 to S5), then pins (S6 to S8), then the mode's platform steps, then gates, monitoring and rollback (S9 to S12), and only then traffic (S13). No opened page states this order; it is assembled from per-platform pages (Finding 1), and the monitoring-before-traffic ordering reads the AWS anti-pattern (D-D21) as a rule.

**Credentials.** Default to a runtime identity or federation in every mode. Use a static key only where the provider offers no identity path (for example a Gemini standard key; the Gemini API also offers service-account-bound authorization keys and OAuth, D-A20), keep it in a secrets manager, and give it an expiry and an owner. Rules D-R16 to D-R28 cover the failure cases.

**Pins.** Default to the pin that cannot move in each mode. In API mode that is a snapshot id. In managed mode it is an explicit deployment version with a deliberate upgrade policy in IaC. In self-hosted mode it is an image digest plus a weights commit hash, served as safetensors only. Read the retirement date from the host that serves the model, not from the model's first-party page (D-R4).

**Prompts and config.** Two patterns are both sourced (S6). This record proposes that the builder defaults to reviewed files in the repository (the default is an open question) with a content hash in the release manifest, because OpenAI is retiring reusable prompt objects and this needs no extra service. Where the build already runs a prompt registry, use version ids or protected labels (plan-gated on Langfuse, D-O10) and record the version id per release; rollback is then a label move bounded by the SDK cache TTL (D-R64).

**Rollout by mode.**
- API: roll forward by config change behind a server-side flag or prompt label, and roll back by reverting it while the previous id is live (S25, D-H22).
- Managed: roll out by second deployment or traffic split; on SageMaker create the alarms first (D-M15); keep the previous unit through a builder-set window (Microsoft mentions about 30 days for embedded teams, D-O14), and delete only after the request count is zero (S34 to S36).
- Self-hosted: roll out with GPU surge capacity planned or `maxSurge` 0, keep the previous revision and its weights cached, and route on inference gauges (S49, S50).

**Readiness display.** The builder shows each readiness row with its source component and one of five results: pass, fail, not applicable (with reason), unknown (with its open question and owner), or not measured (a measurement row the user has not run). A `fail` outcome on a rule with fixed `error` severity blocks the ship decision; a passing `error` rule does not. A failed `warning` rule can be accepted with a recorded reason, following #35. The not applicable and not measured display states, and written acceptance of a reviewable unknown, are this record's proposed convention. They do not rewrite evaluator outcomes or override a ruleset's `on_unknown: block` disposition.

### What the builder shows when a readiness check fails

| result | shown as | effect on go or no-go |
|---|---|---|
| `fail` on a rule with fixed `error` severity | the rule id, the condition met, the suggested correction | blocks until corrected |
| `fail` on a rule with fixed `warning` severity | the rule id and correction, with an "accept with reason" control | allowed once accepted; the reason is stored with the build |
| unknown | the hypothesis or open question, its owner and the date it is due | a reviewable unknown requires written go/no-go owner acceptance; `on_unknown: block` still blocks |
| not measured | the measurement the user must run (cold start, rollback time, load test) | blocks the readiness rows that depend on it |
| not applicable | the false applicability predicate and reason (for example, an absent optional component); required-presence rules still evaluate | none |

## T4 deployment-readiness inputs (2026-10-18; proposal)

The [paired T6 receiving dispositions](https://github.com/Pick-Your-AI/pick-your-ai-research/issues/35#issuecomment-6245652021)
request three deployment capabilities beyond R18/S10. Receive these as
configuration-bound evidence inputs, referencing the existing
[T4 MCP rule proposals](../T4-agents-integrations/mcp-servers.md), rather than
copying their provisional assertions into an adopted deployment ruleset.

| Readiness input | Existing T4 rule identifier | Required evidence and limit |
| --- | --- | --- |
| Local subprocess spawning and locality | `rule.t4.mcp.stdio.colocation` | The selected client runtime can start the selected stdio server in the required local execution boundary. A generic target type or an installed executable alone does not prove that path works. |
| Reachability and isolation for the selected server | Historical `rule.t4.mcp.remote.air-gapped`, narrowed into W-R8/CD-4 by the #40 review below | The selected endpoint/transport is reachable under the actual egress/residency policy. For an air-gapped workload, no enabled runtime connection may leave the selected isolation boundary, and all runtime artifacts must be present inside it. Apply these requirements to provider-operated and self-operated components alike. |
| Available authorization flow | `rule.t4.mcp.auth.flow-available` | Identify an actual supported interactive path or independently evidenced non-interactive alternative for the selected framework/server/target. A browser somewhere on the operator's laptop does not prove it is usable in the deployment's flow. |

**Isolation reconciliation (2026-10-18).** [The actual #40 disposition](https://github.com/Pick-Your-AI/pick-your-ai-research/issues/40#issuecomment-6242626523) routes the earlier operator/trust proxy to [W-R8](../T0-configuration/workload-use-case.md#w-r8-air-gapped-builds-have-no-external-connections). Record endpoint membership and each connection's provisioning/runtime lifecycle and enabled state; an absent inventory is unknown. A provider-run installation inside the boundary can satisfy this isolation input with complete evidence. Keep the historical T4 proxy as provenance while #40 owns the versioned representation; no frozen rule is changed here.

For all three, retain selected component versions, execution boundary, evidence
locator/date and outcome separately. Unknown capability is not false evidence of
incompatibility, but blocks a positive readiness claim until resolved. A known
required capability that the target denies fails; a non-applicable input is skipped.
A stored credential reference alone establishes no validity, audience, scope,
consent, refresh path or permission to configure credentials. No credential is
collected or transmitted by this research.

Synthetic examples, not executed deployment tests: a stdio-only server with a
known no-process target fails; a server requiring a runtime connection outside an
air-gapped boundary fails, regardless of operator; an OAuth-only server without an available supported authorization
path fails; an unexamined non-interactive alternative remains unknown rather than
passing because a key reference exists. With no selected MCP server, these
conditional inputs are skipped. An evidenced capability still needs the applicable
R18/S10 and #35 controls, and does not certify the whole deployment.

These inputs remain proposed versioned operands for #40, with #27 protocol and
#25 framework evidence. Managed agent runtimes priced in L48 are still a separate
