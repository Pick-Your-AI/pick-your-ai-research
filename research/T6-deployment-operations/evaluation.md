## User decision

How will the user know whether the build meets its quality, safety, latency, and cost targets?

The builder answers this per build. The answer depends on the workload declared in T0 (#2), on which optional workstreams are active (T3 retrieval, T4 tools and agents, T5 fine-tuning), on the deployment mode and data sensitivity declared in T0, and on the guardrails chosen in #35. Running the evaluations is implementation and belongs to the builder's user; this record decides which evaluations apply, what each needs, and what must be recorded before a number can be displayed or used as a gate.

Mode labels follow [merged T0 #81](../T0-configuration/deployment-mode.md): provider-operated shared capacity is **API**, provider-operated dedicated or reserved capacity is **managed**, and user-operated serving is **self-hosted**. Classify each serving component by its operator and capacity, not by provider name. Evaluation adds a separate axis, **evaluator placement**: where the harness, judge model and result store run. A self-hosted build can send outputs to an eligible hosted judge if its data policy permits, and an API or managed build can run a local harness. Platform evaluation services do not make the evaluated build managed.

Three findings shape the record. First, no primary source gives a recommended pass threshold for any evaluation; the only numbers are tool defaults (DeepEval 0.5, Azure quality evaluators pass at 3 of 5, Azure safety default 3 on a 0 to 7 scale, Promptfoo pass rate 100 percent) and illustrative examples from vendor pages, none presented as a recommended threshold, so every threshold in this record is builder-set and labelled hypothesis. Second, no number in this record is measured by us: every figure is published by the cited page or estimated here with its formula. Third, OpenAI's Evals platform is being retired (read-only 2026-10-31, shutdown 2026-11-30), so it is excluded from every recommendation.

Source follow-up, checked 2026-10-18: the lm-evaluation-harness TemplateAPI guide limits likelihood/MCQ tasks to completion endpoints; a chat-completion route does not support that scoring operation. Check the exact backend and task protocol before treating E-R65's API route as eligible ([F02](sibling-reconciliation.md)). Microsoft separately documents pre-training harm screening and a post-training deployment assessment for its fine-tuning service, with predefined evaluation filters independent of customer content-filter configuration and a request process for modified thresholds. These provider assessments do not replace paired base/fine-tuned regression evidence ([F04](sibling-reconciliation.md)); no screening job was run here.

## Compatibility proposals

**Source checked** means checked against primary documentation, not independently reproduced.

**Rule interpretation (candidate revision 0.2).** Each row has one fixed v1 severity (`error`, `warning` or `info`), separate from outcome (`pass`, `fail`, `unknown`, `skipped`). The condition describes the violation: known applicable violation is `fail`; known absence of that violation is `pass`; non-applicability is `skipped` with `not_applicable`; missing eligible inputs are `unknown` with `missing_evidence` and `on_unknown: review`. Resolve conflicts using #41's scope, version/date and authority order before taking the conservative equal-rank numeric value, flagged disputed. Only missing eligible evidence or genuine unresolved ties yield `unknown`; conflict alone does not. Hypotheses remain unaccepted and cannot drive production verdicts. ## Reproducibility criteria for displayed benchmark comparisons

Research question 2. A cited benchmark number may be displayed only with the fields below; the tier decides how it is displayed. Fields are drawn from the lm-eval authors' best-practices checklist (exact prompts, model outputs, no copied cross-paper results; harness and codebase version as the de facto reporting standard, E-B6), HELM's prompt-level transparency (E-B2), MTEB's results schema (dataset_revision, mteb_version; docs.mteb.org/api/results, E-N205), tau2-bench and Terminal-Bench variance reporting (E-A7, E-A10, E-K9), HarmBench's fixed N and split (E-F1), Artificial Analysis's measurement envelope (E-L4, E-B4), and Miller's statistical guidance (E-B15). The tier boundaries are E-H12.

Required fields per displayed number: benchmark name and version; harness or scaffold name, version and commit; attempt policy (single attempt versus best-of-k) and tools; task version and subset; model version string, provider, precision or quantisation; prompt template and shot count; decoding settings (temperature, max tokens, seed); number of trials and reducer (pass@k, pass^k, mean); judge or classifier model and version, and user-simulator model where one exists; n and a 95 percent interval; measurement location, tier and concurrency for latency; container resource limits, timeouts and worker counts for agentic suites; access date and page date; number label (published or estimated; measured only when the user ran it).

| tier | definition | display | examples from the catalog |
|---|---|---|---|
| A reproducible by the user | public data, public harness, all fields present, no private judge | number with interval, n and version; may feed a gate only when re-run by the user on the chosen deployment (E-R50) | BEIR, HarmBench, XSTest, BBQ, JBB-Behaviors, lm-eval tasks with version key |
| B reproducible with caveats | public harness but version-sensitive, judge-dependent, or run on a provider variant; fields present | number with interval, version string and a caveat line; never a gate | MTEB (version), SWE-bench (release), tau2 (v1.0.1, simulator), Terminal-Bench, BFCL, HELM Capabilities (Turbo variants), Epoch, Artificial Analysis, LiveBench (release date) |
| C indicative only | private data, confidential judge, pre-release testing, retired source, or fields missing | label only ("indicative", "vendor-reported, harness unknown", "retired source"); no ranking, no threshold, no gate | AILuminate official grade, Scale SEAL private sets, LMArena, RTEB private part, Open LLM Leaderboard archive, any vendor-reported score without a harness version (E-R49) |

### Alignment with the adopted #41 evidence policy

The [merged #41 policy](../T0-configuration/catalog-data-sources.md#evidence-grades-and-labels) already adopts the R1–R15 reproducibility tuple from [#115 at `9f403b4`](https://github.com/Pick-Your-AI/pick-your-ai-research/blob/9f403b4252ad646fd1f75f73da2ce4fc02bb7991/research/T6-deployment-operations/evaluation.md#benchmark-reproducibility-criteria). That adopted minimum applies to this record's displayed comparisons in addition to the fields above:

| Adopted field | Required detail retained when applying this record |
|---|---|
| R1–R3: evaluation, task/data and model identities | Suite version/commit, task configuration and dataset revision/content hash, exact model snapshot |
| R4–R6: runtime, inference and hosting | Provider route or engine **and version**; precision/quantization, **context limit**, chat template; hardware device/count or relevant API region |
| R7–R9: prompt, sampling and load | Prompt/few-shot format and harness version, temperature/seed/run count, concurrency **and arrival process** |
| R10–R12: metric, measurement and uncertainty | Exact metric/aggregation/percentile; budgets/timeouts/turn limits/**cache state**; standard error or interval **with its dependence model** |
| R13–R15: date, source and limitations | Actual **measurement date**, not only access/publication date; primary URL **and claim-level evidence grade**; contamination status, judge identity and excluded items |

For a one-factor comparison, exactly one independent experimental control may differ. Count precision/quantization, context limit and chat template separately rather than treating their bundled R5 field as one control. Source identity, measurement date and uncertainty are evidence metadata, not additional experimental factors. A known incomplete protocol or known multiple-control change presented as comparable is `fail` with an explanatory reason; use `unknown` only where the necessary evidence cannot be determined. This applies the existing #41 policy and does not create a new executable rule or infer a benchmark result.

Tiers A–C and their boundaries remain this record's E-H12 proposal; they do not replace the adopted tuple or grant reuse rights. Apply [#60's source-by-use decisions](../market/rights-validation.md) separately before displaying any score. In particular, a tier B example involving Artificial Analysis is a methodological classification, not permission to use its data in this product. Keep unavailable fields unknown; do not synthesize missing run metadata.

Run-to-run determinism of hosted APIs at temperature 0 (seed, fingerprint, batch-dependent nondeterminism) was not researched in this pass and is an open question; until it is, tier A for API-mode numbers means "re-run within the reported interval", not bit-identical.

## Recommendation and rationale

The builder should treat evaluation as a per-build plan with four parts: the workload row, the safety pair, the latency-and-cost measurement, and a regression gate on a dataset the user owns.

- **Default harness by mode.** API: Promptfoo (deterministic assertions plus model-graded with an explicit grader) or Inspect, run in the user's CI, datasets in the user's repository. Managed: the platform's evaluators for what they do well (Bedrock programmatic and RAG jobs; Vertex computation-based and rubric metrics; Azure GA quality evaluators) with the same local harness for anything the platform gates by region or marks preview. Self-hosted: lm-eval or lighteval for likelihood tasks, Inspect or DeepEval with a local judge for judged metrics, GuideLLM or vllm bench for latency, Langfuse open-source or Phoenix as the result store. OpenAI Evals is never recommended (E-R1).
- **Judge policy.** A different family from the generator where the stack allows; otherwise name the pairing. Pin the version. Keep a human-labelled agreement sample before any judged metric gates a release (G3).
- **Safety.** Harmful and benign suites together, same configuration, re-run after any tuning or guardrail change (G5). Red-teaming against a hosted provider waits for the authorisation question (E-H2).
- **Latency and cost.** Measured by the user, streamed, caches off, production tier, target region, with the provider's own usage fields for cost (G6). Published provider and third-party numbers are display-only.
- **Public benchmarks.** Selection priors only, shown with the reproducibility fields and tier (G11). Vendor-reported scores without a harness version are labelled and never ranked (E-R49).
- **Workload specifics.** Classification: label F1 with the averaging stated, not a platform token-overlap F1; extraction: schema-valid rate and field accuracy as two numbers. Summarisation: faithfulness by an NLI model or a calibrated judge, ROUGE only against reviewed references. Code: pass@1 at production decoding on the build's own repository tasks, every execution in a sandbox, public code benchmarks cited with scaffold, attempts, trials and version. Chat and content: a held-out set of the build's own conversations, pairwise runs in both orders with a length-controlled score, conversation-level evaluators for multi-turn builds, arena scores as shortlisting priors only.
- **Cost of evaluation.** Judge tokens are a line in #39: Azure safety evaluators 0.02 and 0.06 USD per 1K tokens (Retail Prices API), Vertex computation-based 0.00003 and 0.00009 USD per 1k characters, Bedrock human tasks 0.21 USD, AgentCore built-ins 0.0024 and 0.012 per 1,000 tokens; independent platforms bill judge calls to the user's own provider key.
