# 4. T2 Product Context

Pick Your AI is intended to provide a **PCPartPicker-style configuration experience for complete AI systems**.

T2 determines where and how selected AI models and supporting services can operate.

```text
T2. Infrastructure
│
├── Hosting
│   ├── Deployment Mode [T0]
│   ├── GPU Availability [T2]
│   ├── Region / Location
│   ├── Networking & Storage
│   └── Pricing / Commitments
│
├── GPU / Compute
│   ├── AI Model [T1]
│   ├── Context Window [T1]
│   ├── Inference Engine [T2]
│   ├── Fine-Tuned Artifacts [T5]
│   ├── Concurrency / Throughput
│   ├── Quantization / Memory
│   └── Hardware Availability
│
└── Inference Engine
    ├── Model Architecture [T1]
    ├── Model Format / Quantization
    ├── Accelerator / Compute [T2]
    ├── Hosting Environment [T2]
    ├── Fine-Tuned Model [T5]
    └── Serving Features / API Surface
```

These relationships are not strictly one-directional.

For example:

- Model selection influences GPU requirements.
- GPU availability constrains which models can run.
- Context length affects KV-cache memory.
- Inference engine support determines which model formats and hardware can be used.
- Quantization changes memory and potentially performance.
- Concurrency and batching alter memory and throughput.
- Hosting limits hardware choices and deployment feasibility.
- Fine-tuned adapters may introduce additional inference requirements.

The research must produce data and compatibility relationships that can eventually support dynamic reevaluation when a user changes a component.

# 8. Track B — #10 GPU / Compute

**Issue:** https://github.com/Pick-Your-AI/pick-your-ai-research/issues/10

**Deliverable:**

`research/T2-infrastructure/gpu-compute.md`

**Canonical kinds:**

- `accelerator`
- `compute_profile`

## Objective

Determine which compute systems can serve particular models under stated workload, precision, context, throughput, latency, and concurrency requirements.

This is a central capability of the Pick Your AI platform.

Research must distinguish **hardware specifications, theoretical capacity, estimated performance, and measured performance**.

## Accelerator categories

Research relevant:

- NVIDIA datacenter GPUs.
- NVIDIA workstation and consumer GPUs.
- AMD datacenter and consumer GPUs.
- Intel GPUs and accelerators.
- Apple Silicon unified-memory systems.
- CPU-only inference.
- Other AI accelerators where materially relevant.
- Multi-GPU systems.
- Multi-node inference architectures.

Do not assume all hardware supports the same inference engines, programming stacks, kernels, model formats, or quantization methods.

## Accelerator catalog fields

Research:

- Manufacturer.
- Product and version.
- Architecture.
- Device memory capacity.
- Memory bandwidth.
- Compute capabilities.
- Supported numerical precisions.
- Relevant matrix/tensor acceleration.
- Host CPU/RAM dependencies.
- Interconnect.
- Power requirements.
- Hardware/software compatibility.
- Driver and toolkit dependencies.
- Multi-device support.
- Availability.
- Published source and date.

Clearly distinguish physical accelerators from provisionable `compute_profile` offerings.

A compute profile may include one or more accelerators, CPUs, memory, networking, and allocation constraints.

## Model sizing methodology

Develop a defensible inference sizing approach incorporating:

- Model architecture.
- Total parameters.
- Active parameters where applicable.
- Weight representation.
- Quantization overhead.
- Tensor metadata and auxiliary parameters.
- KV-cache memory.
- Attention architecture.
- Number of layers.
- KV heads and head dimension.
- Context length.
- Batch size.
- Concurrency.
- Runtime allocations.
- Activation and temporary buffers.
- CUDA graphs or equivalent runtime allocations where applicable.
- Fine-tuning adapters or merged artifacts.
- Fragmentation and operational headroom.

Do not assume a simplified calculation such as:

`parameters × bits / 8`

is sufficient to establish practical model compatibility.

It may be one component of a broader estimate.

For mixture-of-experts models, distinguish total resident weights, active parameters per token, architecture-specific behavior, and implementation-dependent offloading.

## Multi-GPU research

Investigate:

- Tensor parallelism.
- Pipeline parallelism.
- Model sharding.
- Weight offloading.
- CPU/GPU hybrid inference.
- Interconnect and communication overhead.
- GPU memory balancing.
- Runtime-specific hardware support.
- Multi-node serving.
- Throughput scaling limitations.

Do not assume multiple GPU capacities can be summed as if they were one unrestricted memory pool.

Compatibility depends on runtime, parallelism strategy, model format, and hardware topology.

## Performance estimation

Research:

- Prompt processing throughput.
- Generation throughput.
- Time to first token.
- Inter-token latency.
- End-to-end latency.
- Concurrent request capacity.
- Continuous batching.
- Memory bandwidth limitations.
- Compute limitations.
- Context scaling.
- Utilization and headroom.

Record benchmark conditions.

Do not present hardware peak compute as an observed model-serving speed.

## Sizing uncertainty

Develop an approach that produces ranges or confidence classifications rather than false precision.

Document:

- Known requirements.
- Estimated requirements.
- Conservative assumptions.
- Workload-dependent variation.
- Hardware constraints.
- Unsupported configurations.
- Missing evidence.

## Sample compatibility scenarios

Research representative examples covering:

1. Small quantized models on consumer GPUs.
2. Models requiring CPU offload.
3. Larger models on datacenter accelerators.
4. Long-context inference.
5. High-concurrency serving.
6. Multi-GPU model distribution.
7. Unsupported acceleration backends.
8. Fine-tuned adapter loading.
9. API-hosted inference where local hardware sizing is not required.
10. Systems with enough weight memory but inadequate operational memory headroom.

Use verified specifications and published measurements for real examples.

Clearly label purely illustrative scenarios as synthetic.

## Acceptance requirements

Issue #10 must deliver:

- Accelerator taxonomy.
- Accelerator and compute-profile comparison fields.
- Evidence-backed hardware candidates.
- Inference memory estimation methodology.
- Performance estimation assumptions.
- Quantization and multi-GPU constraints.
- Explicit uncertainty and headroom policy proposals.
- Model ↔ GPU compatibility rules.
- Distinction between estimates and measurements.
- Reviewed and merged decision record.
- Confirmed T1, T5, and T6 handoffs.

# 14. Research and Verification Standards

Treat every significant technical claim as requiring evidence.

## Primary sources

Prefer:

1. Official GPU manufacturer specifications.
2. Official inference engine repositories.
3. Versioned engine documentation.
4. Hosting provider specifications and pricing.
5. Official model architecture and model-card documentation.
6. Published reproducible benchmarks.
7. Independent technical measurements with stated conditions.

Community discussions may help identify candidates or operational limitations, but should not replace verified specifications.

## Evidence classifications

Distinguish:

- Primary documentation.
- Vendor claim.
- Independent measurement.
- Estimate.

Record hypotheses and unknowns separately; they are not evidence grades.

Record dates, versions, assumptions, and test conditions.

## Numeric evidence requirements

For performance or memory figures, record as applicable:

- Model/version.
- Weight format.
- Precision/quantization.
- Hardware.
