## Android acceptance requirements

Apply these to each relevant child alongside its exact criterion set. Record inapplicability with its accepted scope decision rather than removing a check.

| Area / epic | Required implementation and observable evidence |
| --- | --- |
| Foundation 02; storage 12; quality 15 | Use the framework selected by Pick-Your-AI/pickyour.ai#67. Pin compatible build tools/dependencies and SDK support; retain clean-checkout and CI logs. Test rotation, backgrounding, low-memory process death, cold start, back navigation, resized windows and upgrade without losing acknowledged edits or opening the wrong draft. Do not depend on a final lifecycle callback to persist data. |
| Persistence 08/11/12 | Durable transactions for draft/revision/head; migration from every supported schema version; corrupt-record/disk-failure recovery without silent destructive reset. Preserve pins and incomplete drafts. Test autosave acknowledgment, undo as a new revision, outbox crash after server commit, idempotent retry, CAS conflicts, cancellation and account isolation. |
| Offline 04/05/12 | Atomically activate complete hash-verified artifacts; retain prior cache on interrupted download. Respect OS/network/battery background limits, disclose unavailable server-only checks, prevent mixed snapshots and late responses replacing current analysis. Background scheduling is not a durability guarantee. |
| Security 11/14 | Least-permission manifest and exported-component audit; safe token custody/Keystore where applicable, TLS policy, backup exclusions and log redaction. Verify grant, denial and revocation. Bound URI/byte/depth imports before decoding; Android document/share flows require explicit acceptance and safe projections. Server authority applies to guests as well as accounts. |
| Links 11/16 | Verify Android App Links with the actual distribution certificate/domain association, hostile URL cases, cold/warm navigation, no automatic draft mutation, revoked shares and browser fallback with no installation. Domain verification grants no object access. |
| Experience 06/15 | TalkBack labels/order/focus, font scaling, RTL, keyboard, reduced motion, contrast and non-color-only outcomes. Exercise supported phone/tablet/foldable and window configurations with real data volume and failure states. Record manual accessibility separately from automated semantics checks. |
| Devices 15 | Approve the support matrix and measurable budgets through existing decision issues. Distinguish emulator results from physical-device evidence, debug from optimized signed release, and measured memory/energy/render/startup from guesses. Check shrinker/serialization, install/update, backup/deletion and signing-sensitive integrations on the exact candidate. |
| Signing and Google Play 16 | Verify actual publisher/account type and access, package identity, key/upload custody and recovery, version codes, AAB provenance, mappings/symbols and release permissions. Recheck current target SDK/native SDK compatibility, policy and account/region-dependent testing conditions. Retain track-delivered install and prelaunch/defect receipts. Data safety, privacy, account deletion, billing and UGC obligations follow actual enabled behavior and current policy. |
| Release/operations 16/17 | Separately evidence upload/submission, review approval, authorized rollout and store availability; then clean-install and upgrade the production build, follow links, complete the core journey and verify API/catalog/telemetry identity. Exercise alerts, source correction, restore, rollout halt and forward-fix; do not assume installed apps can be remotely downgraded. Support routes must deliver to an agreed monitored destination; diagnostics need redaction preview and no automatic upload. |
