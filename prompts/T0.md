# 3. Product Vision and T0 Responsibilities

Pick Your AI is a **PCPartPicker-style configuration system for artificial intelligence**.

Users should be able to assemble compatible AI stacks, understand tradeoffs, compare cost and performance, and save or share reproducible configurations.

T0 is the foundation of the entire configuration system.

It determines:

- What the user wants to accomplish.
- The requirements and constraints of that workload.
- How the AI system will be deployed.
- Which components and options are applicable.
- How configuration data is represented.
- How compatibility rules are structured.
- Where catalog facts and pricing evidence originate.
- How uncertainty and data freshness are communicated.
- How builds are saved, compared, shared, and revalidated.

## Central architectural requirement

The configuration process must not assume a strictly linear dependency hierarchy.

Selecting a model can constrain GPUs. Selecting a GPU can constrain models. Selecting an inference engine can affect both.

Workload changes can invalidate previously selected infrastructure.

Changing deployment mode can alter provider, hosting, data residency, and cost requirements.

The research must define a system capable of evaluating these relationships without introducing artificial cyclic blockers into the GitHub execution workflow.

T3, T4, and T5 are optional capabilities that must disappear cleanly when not selected.

## Research objective

Define a technically meaningful deployment-mode taxonomy that constrains applicable models, infrastructure, APIs, storage, operational responsibilities, and costs.

## Required deployment categories

### API

A hosted provider exposes model functionality through an API.

Research:

- Provider-managed inference.
- API capabilities.
- Data handling.
- Usage billing.
- Rate and quota limits.
- Regional availability.
- Operational responsibility.

### Managed

A third party manages some or all of the deployment environment, such as dedicated endpoints or managed inference infrastructure.

Research:

- Responsibility boundaries.
- Runtime control.
- Model selection flexibility.
- Hardware choices.
- Autoscaling.
- Dedicated endpoint models.
- Infrastructure access.
- Capacity-based pricing.

### Self-hosted

The user operates inference infrastructure directly.

Research:

- Local workstations.
- On-premises servers.
- Private cloud.
- Rented bare-metal infrastructure.
- Self-managed GPU instances.
- Model weight and licensing requirements.
- Inference engine compatibility.
- Operational costs and responsibilities.

### Hybrid

Different components may operate in different environments.

Examples:

- Hosted model API with local RAG.
- Self-hosted inference with external tool APIs.
- Managed inference with self-hosted knowledge storage.
- Local development with hosted production deployment.

## Critical architectural decision

- Compatibility logic.
- User experience.
- Network boundaries.
- Data residency.
- Security controls.
- Infrastructure selection.
- Pricing.

- Required.
- Optional.
- Inapplicable.
- Conditionally applicable.
- Unknown.

`research/T0-configuration/component-schema-compatibility.md`

## Research objective

Validate and complete the foundational specification that represents AI components, user selections, dependency relationships, compatibility rules, uncertainty, and recomputation.

This is the central architectural research issue for the entire Pick Your AI platform.

## Mandatory starting point

The merged v1 contract already defines canonical component kinds and shared schemas.

**Do not rewrite it or replace it with a competing data model.**

Review its coverage, identify remaining gaps, and propose changes through the established governance process.

The current contract covers 29 canonical component kinds across T0–T6.

## Required architectural areas

### A. Catalog entities

Research:

- Stable component identifiers.
- Canonical kinds.
- Provider relationships.
- Versions and variants.
- Lifecycle state.
- Source provenance.
- Availability.
- Product specifications.
- Category-specific fields.
- Compatibility attributes.

Distinguish component identity from a particular version or deployment instance.

### B. Configuration selections

Research:

- Selected component references.
- Per-selection settings.
- Build-specific parameters.
- User constraints.
- Role or function within a build.
- Optional components.
- Repeated instances.
- Missing selections.
- Version references.

Separate canonical catalog facts from user-specific configuration choices.

### C. Dependency graph

Define:

- Required dependencies.
- Optional dependencies.
- Conditional dependencies.
- Compatibility relationships.
- Derived constraints.
- Downstream impacts.
- Missing prerequisites.
- Cross-tier relationships.

Distinguish the **product compatibility graph** from the **GitHub issue execution graph**.

The product graph may contain feedback loops. The GitHub execution graph should not contain artificial blocking cycles.

### D. Compatibility rules

Use the v1 contract semantics.

**Severity:**
- `info`
- `warning`
- `error`

**Evaluation outcome:**
- `pass`
- `fail`
- `unknown`
- `skipped`

Define how these values interact without treating severity as the result of a compatibility check.

Every rule proposal should identify:

- Rule ID.
- Participating component kinds.
- Relevant fields.
- Applicability conditions.
- Assertions and comparisons.
- Units and thresholds.
- Missing-data behavior.
- Severity.
- Outcome semantics.
- Source evidence.
- Explanation.
- Suggested correction.
- Version and scope.

### E. Cross-tier recomputation

Research how selections are reevaluated when requirements change.

Examples:

- Model change affects GPU fit.
- GPU change affects supported models.
- Inference engine change affects model formats.
- Context change affects capacity.
- Deployment mode change affects provider availability.
- RAG activation introduces knowledge dependencies.
- Agent activation introduces tool and guardrail requirements.
- Fine-tuning introduces training compute.
- Pricing changes invalidate cost estimates.

Propose an explicit dependency-propagation strategy.

Explain how cycles are handled, how recomputation terminates, and how unknown data affects conclusions.

### F. Versioning

Review:

- Schema versioning.
- Catalog item versions.
- Rule versions.
- Dependency graph versions.
- Provider/model snapshots.
- Historical build compatibility.
- Migration and backward compatibility.

The current v1 intake has an identified limitation: catalog references use IDs without explicit versions, and the intake currently restricts proposals to one version per catalog ID to avoid ambiguous resolution.

Evaluate that limitation and propose a versioning solution if the research demonstrates a need.

Do not silently relax validation or introduce historical versions under an ambiguous ID.

### G. Evidence and uncertainty

Compatibility rules must not imply certainty where evidence is incomplete.

Define handling for:

- Missing specifications.
- Conflicting sources.
- Outdated facts.
- Estimates.
- Provider claims.
- Independent measurements.
- Conditional support.
- Unavailable runtime tests.

Never assume unknown means compatible.

### H. Worked examples

Create documented, version-aware examples covering:

1. Model ↔ GPU memory.
2. Model ↔ inference-engine format.
3. Context ↔ KV-cache capacity.
4. Provider ↔ deployment mode.
5. Optional RAG dependencies.
6. Optional agent/tool dependencies.
7. Fine-tuned artifact ↔ inference engine.
8. Multiple valid hosting options.
9. Compatibility becoming unknown after source expiration.
10. Revalidation after a previously selected component changes.

Use synthetic fixtures clearly identified as examples unless real verified product data is available.

## Contract governance

For any proposed schema change:

1. Describe the current limitation.
2. Reference the canonical schema or field.
3. Provide examples demonstrating the problem.
4. Explain downstream consequences.
5. Identify affected owners.
6. Describe compatibility and migration behavior.
7. Include tests.
8. Request appropriate review.
9. Preserve v1 reproducibility.
10. Merge only through the accepted contract process.

Do not patch generated schema artifacts alone.

## Acceptance

Issue #40 requires:

- Reviewed canonical schema analysis.
- Documented compatibility semantics.
- Worked examples.
- Defined unknown handling.
- Dependency and recomputation strategy.
- Versioning decisions or explicit proposals.
- Defined contribution format.
- Accepted handoffs from affected component owners.
- Validated and merged decision record.
- No unresolved contract inconsistency concealed by synthetic fixtures.
