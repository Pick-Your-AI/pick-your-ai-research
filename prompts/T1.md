# 8. Track C — Issue #7: Context Window

**Issue:** https://github.com/Pick-Your-AI/pick-your-ai-research/issues/7

**Deliverable:**

`research/T1-model-selection/context-window.md`

**Canonical kind:** `context_policy`

## Research objective

Determine how Pick Your AI should evaluate context-window suitability based on model constraints, provider limits, tokenizer behavior, workload requirements, output reservations, GPU capacity, and cost.

## Context taxonomy

Research and distinguish:

- Advertised context limit.
- Provider-enforced context limit.
- Maximum input tokens.
- Maximum output tokens.
- Combined input/output limits.
- Requested context.
- Reserved output capacity.
- Effective usable context, only when adequately supported by evidence.
- Provider-specific context overrides.
- Long-context pricing thresholds.
- Caching and token-accounting behavior.
- Multimodal input accounting where applicable.

A model's advertised context size must not automatically be treated as guaranteed effective retrieval or reasoning capacity.

## Tokenization

Research:

- Tokenizer identity.
- Tokenizer versions.
- Special tokens.
- Model-specific tokenization.
- Provider accounting differences.
- Token estimation from text.
- Multimodal token accounting when documented.
- Uncertainty in approximate token estimates.

Do not assume character count or word count yields identical token counts across models.

## Context compatibility

Evaluate relationships between:

- Selected model.
- Provider-specific limits.
- Requested input context.
- Output reserve.
- Total context budget.
- Inference engine.
- GPU memory.
- KV-cache implications.
- Concurrency.
- Optional RAG and agent memory.
- Price tiers.

The builder should eventually distinguish:

**Fits:** `pass` against eligible documented limits; label evidence unverified until independently reproduced.

**Does not fit:** `fail` against an eligible hard limit, with evidence status recorded separately.

**Conditional:** The configuration depends on a documented condition.

**Unknown:** Available evidence is insufficient.

Use the canonical rule contract's actual outcomes and severities when encoding these conclusions.

## Hardware boundary

T1 determines context requirements and relevant model-level constraints.

T2 #10 owns the GPU capacity calculations, KV-cache sizing methodology, runtime overhead, and memory feasibility.

T1 must provide the inputs T2 needs without duplicating T2's calculations.

## Pricing boundary

T1 documents provider-specific token and long-context pricing facts.

T6 #39 owns cost calculation, aggregation, and uncertainty handling.

## Required example scenarios

Document cases such as:

1. Requested context comfortably within the provider's supported limits.
2. Requested context exceeding the model limit.
3. Output reservation causing the combined limit to be exceeded.
4. Provider advertising a lower limit than the base model's published limit.
5. A model technically supporting a context length but requiring more hardware memory than available.
6. A long-context tier changing API cost.
7. A local tokenizer estimate differing from provider billing.
8. Multimodal token usage that cannot be accurately estimated with text-only accounting.
9. An unavailable or unverified effective-context claim.
10. RAG or agent memory increasing context requirements.

For each example, separate outcome from evidence: checked documentation, independent verification, estimates, conditions and unknowns. Apply the #88 owner position linked in SHARED.md: use the conservative upper bound for straddling context estimates, default to the native limit without evidence of extended configuration, recount after transformations, and check quality only when a workload quality target exists. Separate answerable licence conditions from offering capability. Reconcile model/engine support and memory fit into the #75 joint-support and memory-fit families; T1 supplies pinned inputs and #10/#11 own sizing/runtime evidence. CD-11's separate input/output budgets remain a versioned #40 proposal.

## Acceptance requirements

Issue #7 is complete when:

- Context-limit definitions are documented.
- Token estimation methodology includes uncertainty.
- Provider overrides are addressed.
- Input/output and combined limits are distinguished.
- Context fit, warning, and unknown rules follow #40.
- T2 agrees to the context/KV-cache interface.
- T3 receives applicable context budgeting requirements.
- T6 receives pricing tier information.
- The decision record is reviewed and merged.
- Existing issue acceptance criteria are fully satisfied.

# 19. Blocker Management

Do not allow one missing external source or delayed review to halt independent research.

For every blocker:

1. Identify the issue and owner.
2. Document the precise missing input.
3. Determine whether the relationship is a true blocker.
4. Complete all unaffected research.
5. Preserve unknown findings explicitly.
6. Link the required decision or handoff.
7. Update readiness accurately.
8. Report the remaining acceptance gap.

Examples:

- Provider model ID unavailable: record a sourced unknown.
- Model architecture unpublished: leave the relevant requirement unverified.
- GPU compatibility not established: coordinate with T2 rather than inventing a hardware recommendation.
- Fine-tuning rights unclear: request T5 review and do not assume permission.
- Missing price: keep pricing incomplete rather than fabricating a rate.
- Schema mismatch: propose changes through #40.
- Pending owner review: leave the corresponding acceptance criterion open.

Continue authorized work until completion or genuine external blockers prevent further progress.
