# 3. Product Vision and T3 Scope

Pick Your AI is a PCPartPicker-inspired platform for configuring complete, compatible AI systems.

T3 represents the optional **Knowledge & Retrieval** capability.

The user may select a model, hosting environment, infrastructure, and inference engine without requiring a knowledge base or retrieval system.

When the user needs AI responses grounded in external or private data, T3 provides the component options and compatibility requirements.

## T3 architecture

```text
T3. Knowledge & Retrieval (Optional)
│
├── Knowledge Base
│   ├── Data Sources
│   ├── Connectors & Authentication
│   ├── Parsing & Ingestion
│   ├── Chunking & Metadata
│   ├── Storage [T2]
│   ├── Access Control
│   └── Synchronization & Deletion
│
├── Embedding Model
│   ├── Input Data Type
│   ├── Model Provider [T1]
│   ├── Hosting [T2]
│   ├── Dimensions & Metrics
│   ├── Language & Modality
│   └── Vector Index Compatibility
│
├── Vector Database (Optional Backend)
│   ├── Embedding Model
│   ├── Vector Dimensions
│   ├── Distance Metrics
│   ├── Metadata Filtering & ACLs
│   ├── Hosting [T2]
│   └── Scaling & Pricing
│
└── RAG & Retrieval Backends
    ├── Knowledge Base
    ├── Retrieval Method
    │   ├── Keyword
    │   ├── Vector
    │   ├── Hybrid
    │   ├── Graph
    │   └── Direct Database / API Lookup
    ├── Embedding Model (When Required)
    ├── Vector Database (When Required)
    ├── Reranking (Optional)
    ├── AI Model [T1]
    ├── Context Budget [T1]
    ├── Evaluation [T6]
    └── Source Citations & Permissions
```

### Fundamental architecture rules

1. T3 is optional.
2. A knowledge base does not automatically require a vector database.
3. A RAG solution may use keyword, vector, hybrid, graph, or direct retrieval.
4. Embeddings are required only when the chosen retrieval architecture depends on them.
5. A vector database may be unnecessary when an existing database or search engine satisfies the workload.
6. Data ingestion, embedding generation, and retrieval are separate concerns.
7. Permissions and deletion must remain consistent across source documents, derived chunks, embeddings, and indexes.
8. Research must support API, managed, and self-hosted configurations where applicable.
9. Compatibility is conditional on versions, formats, dimensions, infrastructure, and workload requirements.
10. Unknown compatibility must never be silently represented as supported.

These requirements must be reflected in the research, proposed compatibility rules, and documented component-selection logic.

# 10. Cross-Component Compatibility Orchestration

The four T3 tracks must produce one coherent configuration model.

Investigate and document the following scenarios.

## Mandatory compatibility scenarios

**Scenario 1 — No knowledge retrieval**

The user configures a model and inference system without T3.

Expected: T3 is omitted without unnecessary errors.

**Scenario 2 — Keyword search without embeddings**

The user selects keyword retrieval over a document corpus.

Expected: The configuration does not require an embedding model or vector database.

**Scenario 3 — Dense vector retrieval**

The user selects an embedding model and vector database.

Expected: Dimensions, metrics, storage, and pipeline requirements are validated.

**Scenario 4 — Embedding dimension mismatch**

An embedding model produces vectors incompatible with the chosen index.

Expected: An explainable incompatibility or conditional remediation is produced.

**Scenario 5 — Model replacement**

The user changes embedding models.

Expected: The configuration identifies when re-embedding, reindexing, or migration is required.

**Scenario 6 — Context budget pressure**

Retrieved chunks consume too much of the selected generative model's context.

Expected: The relevant warning or constraint is represented.

**Scenario 7 — Permission-restricted documents**

The retrieved corpus contains documents with different user access rights.

Expected: The required ACL enforcement and potential leakage risk are exposed.

**Scenario 8 — Data deletion**

A source document is deleted or permission is revoked.

Expected: The research defines how derived chunks, embeddings, indexes, and caches must be handled.

**Scenario 9 — Managed versus self-hosted**

A component is unavailable or restricted in a deployment environment.

Expected: Hosting constraints and alternatives are documented.

**Scenario 10 — Direct retrieval without vector DB**

A user connects to a structured source and retrieves information through direct queries.

Expected: The system permits this architecture without forcing unrelated vector infrastructure.

- Input selections.
- Participating component kinds.
- Actual prerequisites.
- Compatibility result or unknown.

- Explanation.
- Suggested correction.
- Evidence.

# 18. Blocker Handling and Continued Execution

A blocked dependency must not stop unrelated work.

2. Identify the blocking issue or missing decision.
3. Preserve all completed findings.
4. Record the blocker and responsible owner.
5. Continue unaffected work.
6. Propose the smallest resolution path.
7. Report what remains outstanding.

Examples:

- Incomplete T1 model research does not prevent investigating embeddings.
- Unresolved hosting pricing does not prevent defining vector compatibility.
- Pending schema review does not prevent completing evidence-backed research notes.
- Missing evaluation methodology does not prevent documenting retrieval architecture.
- Unanswered cross-team review does not justify claiming a handoff is accepted.
- An unavailable vendor specification must remain unknown rather than fabricated.

Do not weaken acceptance criteria to manufacture completion.
