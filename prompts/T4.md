# 3. Product Context

Pick Your AI is a **PCPartPicker-style AI stack configuration platform**.

A user should be able to configure a complete AI system while understanding compatibility, dependencies, operational requirements, performance, and costs.

T4 represents the optional **Agents & Integrations** tier.

```text
T4. Agents & Integrations (Optional)
│
├── Agent Framework
│   ├── AI Model [T1]
│   ├── Inference Engine [T2]
│   ├── RAG [T3] (Optional)
│   ├── Tools & APIs [T4]
│   └── Memory [T4]
│
├── Tools & APIs
│   ├── Agent Framework
│   ├── Authentication & Permissions
│   ├── Guardrails [T6]
│   └── API Costs [T6]
│
├── MCP Servers
│   ├── Client / Framework Compatibility
│   ├── Protocol Version & Transport
│   ├── Hosting [T2]
│   ├── Authentication
│   └── Security Controls [T6]
│
└── Agent Memory
    ├── Framework & State Management
    ├── Context Window [T1]
    ├── Storage [T2/T3]
    ├── Retrieval [T3] (Optional)
    └── Privacy, Retention & Deletion
```

T4 must be completely omittable from a configuration.

A build without agents must not require agent frameworks, MCP servers, memory systems, or tool integrations.

The goal is to enable users to discover, select, compare, and validate compatible agent-related components—not to mandate a specific agent architecture.

# 7. Track B — Issue #26: Tools & APIs

**Issue:** https://github.com/Pick-Your-AI/pick-your-ai-research/issues/26

**Deliverable:**

`research/T4-agents-integrations/tools-apis.md`

**Canonical kinds:** `tool`, `integration`

## Research objective

Define how the builder discovers and evaluates tools, external APIs, and integrations that agents can invoke.

Determine compatibility, authentication, permissions, side effects, reliability, and operational constraints.

## Research categories

Investigate relevant classes of runtime tools:

- HTTP/API requests.
- Search and browsing.
- Database access.
- File and document operations.
- Code execution.
- Communication and messaging.
- Productivity applications.
- Developer platforms.
- Cloud infrastructure APIs.
- Workflow automation.
- Enterprise systems.
- Specialized domain tools.

Do not attempt to exhaustively enumerate every publicly available API.

Prioritize a reusable taxonomy, representative candidates, and verifiable decision criteria.

## Required metadata

- Stable tool identifier.
- Provider and version.
- Tool category.
- Supported framework interfaces.
- Input/output contracts.
- Authentication method.
- OAuth scopes or equivalent permissions.
- Credential handling requirements.
- API limits.
- Required network access.
- Side-effect classification.
- Data-access scope.
- Approval requirements.
- Idempotency and retry considerations.
- Failure behavior.
- Usage and pricing units.
- Licensing or usage restrictions.
- Evidence and verification date.

## Risk taxonomy

Develop classifications covering:

**Read-only:** Operations that retrieve information without intentionally modifying external state.

**Write:** Operations that modify data or external resources.

**High-impact:** Operations that can delete data, change privileges, incur substantial costs, or affect external systems.

**Irreversible:** Operations that cannot reliably be undone.

Define human-approval and least-privilege requirements, routing the resulting guardrail policy to T6 #35.

These categories are proposed research classifications. The v1 `tool.spec.side_effect` enum is only `read_only` or `mutating`; record impact and reversibility separately in notes and route new structured fields through #40. Review each API's actual security behavior.

## Boundary requirements

T4 owns runtime actions and live API integrations.

T3 #13 owns user knowledge-source ingestion, synchronization, and data-source semantics.

Avoid duplicate catalogs for the same provider when an integration has both knowledge-ingestion and runtime-action functions. Preserve distinct capabilities and ownership boundaries.

## Acceptance

Issue #26 requires:

- A normalized tool/integration taxonomy.
- Evidence-backed representative catalog research.
- Explicit authentication and permission metadata.
- Side-effect and approval classifications.
- Operational and pricing considerations.
- Cross-tier security handoff to #35.
- Pricing handoff to #39.
- Reviewed and merged decision record.

- Trust boundaries.
- Permission scope.
- Tool discovery and invocation.
- Failure handling.
- Operational dependencies.
- Security updates and maintenance.
- Licensing and commercial restrictions.

## Compatibility requirements

Research:

- Agent framework ↔ MCP client capability.
- MCP client ↔ server protocol version.
- Transport compatibility.
- Local versus remote hosting.
- Authentication requirements.
- Tool capability exposure.
- Deployment feasibility.
- Guardrail requirements.

For each proposed rule, distinguish:

- `pass`, with checked/independently verified evidence status explicit.
- `fail`, with the deciding eligible evidence recorded.
- Conditional support, with the condition and resulting outcome stated.

- Credential disclosure.
- Prompt injection through returned content.
- Unauthorized side effects.

# 17. Failure and Blocker Handling

Do not stop the entire assignment because one track encounters an external dependency.

When a blocker occurs:

1. Identify its exact cause.
2. Determine whether it is a real execution blocker or merely an informational input.
3. Link the affected issue and owner.
4. Record what has already been completed.
5. Continue independent work.
6. Identify the smallest decision or change that would resolve the blocker.
7. Report outstanding acceptance criteria.

Examples:
